## 1. 从 falconx-lite 复制什么、怎么改

### 1.1 复制源和原则
- **复制源**：falconx-lite 远程 `staging` `2583328`（2026-10-24 用 `git ls-remote` 核对，C68）。只复制文件，**不带 git 历史、不带任何数据和配置值**（需求第 14 节）。

## 3. 数据库设计

### 3.1 约定（沿用 falconx-lite）
- 表名以模块名开头，只由该模块读写；跨模块只调 `api`。
- 金额 `DECIMAL(24,8)`（NF-07）；下注金额、派彩、抽成在业务上只有 2 位小数（第 4.1 节），数据库仍用 8 位，方便和 falconx-lite 的钱包、账本共用。
- 时间 `DATETIME(3)`，UTC。
- 对外编号用雪花 ID 列 `public_no`（字符串返回，falconx-lite 约定 25）；内部主键自增 `id`。
- **只增不改**的表（审计类）：`market_status_log`、`market_fee_change`、`market_clarification`、`resolve_record`、`resolve_source_fetch`、`settle_item` 的金额列、`ledger_entry`、`admin_audit_log`：应用里没有对应的 UPDATE / DELETE 语句，测试扫描 Mapper XML 检查。
- 状态字段用 `VARCHAR(24)` + 应用里的枚举；每张有状态的表带 `version INT`。

### 3.2 账本（从 falconx-lite 的 `trading_account`、`trading_ledger` 改）

**`ledger_account`**（每个客户一行；平台另有两行）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | |
| `kind` | VARCHAR(24) | `USER` / `PLATFORM_REVENUE`（抽成 + 尾差）/ `PLATFORM_COMPENSATION`（补偿支出） |
| `user_id` | BIGINT NULL | 客户的用户 id；平台账户为空 |
| `available` | DECIMAL(24,8) | 可用余额 |
| `bet_locked` | DECIMAL(24,8) | 下注锁定（客户端"下注中"） |
| `withdraw_frozen` | DECIMAL(24,8) | 提现冻结 |
| `created_at`、`updated_at` | | |

- 唯一：`uk_ledger_account_user (user_id)`、`uk_ledger_account_kind_platform`（平台账户每种只有一行：`kind` 上的唯一键配合 `user_id IS NULL`，用生成列 `platform_key = IF(user_id IS NULL, kind, NULL)` 加唯一键）。
- CHECK：`kind = 'PLATFORM_COMPENSATION' OR (available >= 0 AND bet_locked >= 0 AND withdraw_frozen >= 0)`：补偿支出账户允许为负（平台自己掏钱，余额是累计支出的相反数），其他一律不能为负。

**`ledger_entry`**（沿用 `trading_ledger`，加一列）

| 列 | 说明 |
|---|---|
| `id`、`account_id`、`bucket`、`entry_type`、`amount`、`value_after`、`biz_type`、`biz_id VARCHAR(128)`、`remark`、`created_at` | 沿用（`biz_id` 已是 128，falconx-lite V29） |
| `ref_market_id BIGINT NULL` | 新增：和哪个市场有关（下注、派彩、退款、补偿） |

- 唯一：`uk_ledger_entry_idem (biz_type, biz_id, entry_type, bucket)`（幂等键，沿用）。
- 索引：`idx_ledger_entry_account (account_id, id)`、`idx_ledger_entry_market (ref_market_id, entry_type)`（彩池对账、AC-39）。

**流水类型和账户变动**（一张表看完所有钱怎么走）

| 业务 | 客户账户 | 平台账户 | 幂等键（biz_type : biz_id） |
|---|---|---|---|
| 下注 | `available −b`（BET_LOCK）、`bet_locked +b`（BET_LOCK） | — | `BET : 下注 id` |
| 结算·赢 | `bet_locked −b`（BET_SETTLE）、`available +(b+G)`（PAYOUT）、`available −F`（FEE） | `REVENUE.available +F`（FEE_INCOME） | `SETTLE : 结算明细 id` |
| 结算·输 | `bet_locked −b`（BET_LOST） | — | 同上 |
| 结算·尾差 | — | `REVENUE.available +D`（SETTLE_DUST） | `SETTLE_RUN : 结算单 id` |
| 退款（取消、作废、E14、E15） | `bet_locked −b`、`available +b`（REFUND） | — | `REFUND : 退款明细 id` |
| 补偿（E13） | `available +x`（COMPENSATION） | `COMPENSATION.available −x`（COMPENSATION_EXPENSE） | `COMP : 补偿明细 id` |
| 充值、冲正、提现冻结 / 解冻 / 出账 | 沿用 falconx-lite（只把"余额"换成 `available`） | — | 沿用 |

**守恒在账本上的样子**：一个已结算市场，Σ(客户 `bet_locked` 的减少) = T；Σ(客户 `available` 的增加 PAYOUT − FEE) + Σ(平台 FEE_INCOME + SETTLE_DUST) = T。彩池对账（第 4.4 节）按 `ref_market_id` 直接从账本合计核对。

## 4. 彩池核心实现

### 4.1 金额：scale 和舍入

| 量 | 类型 / scale | 舍入 | 代码 |
|---|---|---|---|
| 下注金额 b | `BigDecimal`，scale ≤ 2，> 0 | **不舍入**：多于 2 位小数直接拒绝（`AMOUNT_SCALE`） | `PoolMath.checkStake` |
| 费率 r | `BigDecimal`，存 `DECIMAL(6,4)`（5.25% = 0.0525） | 后台输入百分比最多 2 位小数，换算时不舍入 | `FeeRate` |
| 中间计算 | `BigDecimal` 精确值，**不用 `double`，不用 `MathContext` 截断** | 只在下表三处舍入 | |
| 盈利 Gⱼ | scale 2 | `b.multiply(L).divide(P_W, 2, RoundingMode.DOWN)`（`divide` 带 scale 时按精确商舍入，等于"向下取整到 0.01"） | `SettleMath.gross` |
| 抽成 Fⱼ | scale 2 | `G.multiply(r).setScale(2, RoundingMode.HALF_UP)`（四舍五入） | `SettleMath.fee` |
| 派彩 Payⱼ | scale 2 | `b + G − F`，不再舍入 | |
| 尾差 D | scale 2 | `L − ΣG` | |
| 概率 %（显示） | 列表 0 位、详情 1 位 | `HALF_UP`；>0 且 <1% 显示"<1%"，>99% 且 <100% 显示">99%"，T = 0 显示"—" | `Odds.percent`（前后端各一份，共用测试向量） |
| 预计赔率 x（显示） | 2 位 | `(Pᵢ + (T − Pᵢ)(1 − r)) / Pᵢ` 用 `divide(.., 2, DOWN)`（向下取整，不夸大），Pᵢ = 0 显示"—" | `Odds.multiplier` |
| 本注预计回报（显示） | 2 位 | 把本注加进奖池后按 G、F 的舍入规则算 | `Odds.expectedReturn` |

- **一份公式，前后端共用测试向量**：`backend/src/test/resources/pool/pool-vectors.json`（例如需求第 3.5 节的两个例子 + 随机生成的 500 组），后端 `PoolMathVectorsTest` 和客户端 `lib/pool.test.ts` 都读它，结果必须逐分一致（客户端的预计回报不能和后端算的不一样）。
- 客户端用已有的 `lib/decimal.ts`（字符串定点小数），不用 JS `number` 算钱。

### 4.2 下注和并发

```mermaid
sequenceDiagram
    participant C as 客户端
    participant B as BetService（pool）
    participant M as MarketApi（market）
    participant A as AccountApi / LedgerApi
    participant DB as MySQL
    C->>B: POST bets {optionNo, amount, clientReqId}
    B->>B: receivedAt = clock.now()；金额格式、最小 / 最大
    B->>DB: 开始事务
    B->>DB: 同一 clientReqId 已有下注？有就直接返回它（幂等）
    B->>M: lockForBet(market)：SELECT … FOR SHARE
    M-->>B: 状态 = 已上架、openAt ≤ receivedAt < closeAt、选项属于该市场
    B->>A: canBet(user)：未冻结、不是员工、KYC 门槛
    B->>A: lock(user)：账户行 FOR UPDATE（同一客户的下注在这里排队）
    B->>DB: SUM(pool_position) where user, market → 是否超上限
    B->>A: apply(available −b, bet_locked +b)（余额不够 → INSUFFICIENT_FUNDS）
    B->>DB: INSERT pool_bet；UPSERT pool_position
    B->>DB: UPDATE pool_option_total SET amount = amount + b（最后一步，锁持有最短）
    B->>DB: 提交
    B-->>C: 下注编号、新的奖池
    B--)C: 事务提交后标记"该市场奖池有变化"，推送任务合并后推（第 7 节）
```

这张图想说明：一次下注就是一个事务；三把锁固定顺序（市场行共享锁 → 客户账户行 → 选项奖池行），不会死锁；同一客户的并发下注在账户行上排队，所以余额和单市场上限都不会超（AC-18）。

**为什么这样选**：

| 问题 | 做法 | 理由 |
|---|---|---|
| 选项奖池并发加 | **悲观锁：原子更新** `UPDATE pool_option_total SET amount = amount + ? WHERE option_id = ?`，放在事务最后 | 乐观锁（版本号）在 100 笔/秒打同一个选项时会大量冲突重试；原子更新只锁一行、持有时间只有"最后一条语句 + 提交"（约 1～3 毫秒【推断】），100 笔/秒分到 2～3 个选项，每行每秒锁住的时间约 15%～30%，有余量 |
| 单客户单市场上限 | 在**客户账户行锁**之内求和 `pool_position`（最多 10 行，走 `(user_id, market_id)` 索引） | 上限是"按客户"的，用客户自己的行锁串行化即可，不需要单独的锁；不同客户互不影响 |
| 余额不超卖 | `LedgerApi.apply` 沿用 falconx-lite：锁账户行、不能为负（数据库 CHECK 兜底） | 已在 falconx-lite 验证 |
| 截止和下注的竞争 | 下注拿市场行**共享锁**；截止任务拿**排他锁**（第 5.2 节） | 截止任务要等进行中的下注提交后才能定格奖池；排他锁排队期间新来的下注会等在后面，拿到锁时看到状态已变，按"已截止"拒绝 |
| 重复提交（双击、网络重试） | `client_req_id` 唯一键，重复请求返回第一次的结果（X-3） | 下注不能撤销（RQ-2），重复扣钱是严重问题 |
| 截止判定 | 只用 `receivedAt`（请求进入应用时的服务器时间）`< close_at`；等于截止时间的拒绝（AC-15） | 需求 3.7 第 4 条 |

**锁顺序和死锁检查**：所有涉及多把锁的操作都按"市场行 → 客户账户行（按 user_id 升序）→ 选项奖池行 / 平台账户行"的顺序。下注（市场 S、一个账户 X、一个选项 X）、截止（市场 X、只读奖池）、结算派彩（市场 X、多个账户按 user_id 升序、平台账户最后）、退款（同结算）、提现（一个账户）之间没有环【推断，S4 用并发测试验证：20 线程混合下注、结算、提现跑 1 分钟无死锁、无超卖】。

**性能估算（NF-01：200 笔/秒，单市场 100 笔/秒，p99 ≤ 500 毫秒）**【推断，AC-70 压测验证】：
- 每笔下注约 8 条 SQL（查幂等、市场共享锁、账户锁、求和、2 条账本、下注、持仓、奖池）+ 1 次提交；200 笔/秒 ≈ 1,600 条语句/秒、200 次提交/秒，MySQL 8.4 在 2 核以上的云盘上可以承受。
- 应用侧：Tomcat 默认线程 200、Hikari 连接池 30（单实例）；单笔服务端耗时目标 < 30 毫秒。
- 风险：同一客户在同一秒连发几十笔（机器人）会在账户行上排队 → 有 `@UserWriteLimited`（每客户每分钟 60 次）挡住。

### 4.3 结算：幂等和事务边界

需求第 3.5 节写的是"同一个事务、幂等"。一个市场最多 10,000 个持仓（NF-03），如果放在一个事务里，要同时锁住最多 10,000 个客户账户行几秒到十几秒【推断】，这期间这些客户在别的市场的下注、提现都会卡住，和 NF-01 的 p99 冲突。所以**分三段**（**AQ-3 已定：B**，Amos 2026-10-25；每批持仓数 `forecast.settle.batch-size` 默认 500，0 = 一个事务完成保留为可配置项）：

```mermaid
flowchart TD
    T["触发：自动裁决成功 / 公示期满无争议 / 争议处理完"] --> P1
    subgraph P1["① 计算（一个事务）"]
        L1["锁市场行；settle_phase 必须是 NONE（否则直接返回已有结算单 = 幂等）"]
        L2["读截止时定格的奖池、赢方持仓（已排除退回的下注）"]
        L3["逐个算 G、F、Pay；算 D"]
```

这张图想说明：钱动之前，所有人的派彩已经算好并通过守恒校验、落在结算单里；之后的派彩可以分批、可以中断后接着做，每一步都只做一次。

**幂等的三道保证**：①`settle_run` 唯一键 `(market_id, kind)`；②`settle_item` 状态条件更新 `UPDATE … SET status='DONE' WHERE id=? AND status='PENDING'`，更新 0 行就跳过；③账本幂等键 `SETTLE : 明细 id`（重复调用返回第一次的结果）。三道任何一道都能挡住重复派彩（AC-23 用三次并发触发测试）。

**结算伪代码**：

```java
// settle/run/SettlementService.java（伪代码）
SettleRun calculate(long marketId, long winningOptionId, String resolvedBy) {
  return tx(() -> {
    Market m = marketApi.lockForSettle(marketId);              // SELECT … FOR UPDATE
    if (m.settlePhase() != NONE) return runs.byMarket(marketId, PAYOUT);   // 幂等
    require(m.status() in [PENDING_RESOLUTION /*自动*/, PUBLICIZING /*期满*/, DISPUTED /*处理完*/]);
    refunds.refundLateAndStaffBets(m);                          // E14、E15：先退，奖池同步减少
    Map<Long, BigDecimal> pool = poolApi.finalTotals(marketId); // 截止时定格（减去退回的）
    BigDecimal T = sum(pool.values());
    BigDecimal PW = pool.getOrDefault(winningOptionId, ZERO);
    if (PW.signum() == 0) return voidMarket(m, "NO_WINNER");    // E1：作废、全额退款
    BigDecimal L = T.subtract(PW);
    BigDecimal r = m.feeRate();                                  // 当时的费率
    List<Position> winners = poolApi.positions(marketId, winningOptionId);
    List<Item> items = new ArrayList<>();
    BigDecimal sumG = ZERO, sumF = ZERO, sumPay = ZERO;
    for (Position p : winners) {
      BigDecimal G = p.amount().multiply(L).divide(PW, 2, RoundingMode.DOWN);
      BigDecimal F = G.multiply(r).setScale(2, RoundingMode.HALF_UP);
      BigDecimal pay = p.amount().add(G).subtract(F);
      items.add(Item.win(p, G, F, pay));
      sumG = sumG.add(G); sumF = sumF.add(F); sumPay = sumPay.add(pay);
    }
    for (Position p : poolApi.positionsExcept(marketId, winningOptionId)) items.add(Item.lose(p));
    BigDecimal D = L.subtract(sumG);
    boolean ok = sumPay.add(sumF).add(D).compareTo(T) == 0
        && D.signum() >= 0
        && D.compareTo(new BigDecimal("0.01").multiply(BigDecimal.valueOf(winners.size()))) < 0;
    SettleRun run = runs.insert(m, PAYOUT, winningOptionId, r, T, PW, L, sumG, sumF, D, sumPay, ok);
    if (!ok) { marketApi.markSettleAbnormal(m); alerts.settleAbnormal(m, run); return run; }
    items.insertAll(run, items);
    marketApi.casSettlePhase(m, NONE, PAYING, winningOptionId, resolvedBy);
    return run;
  });
}

void payBatch(SettleRun run) {                    // PayoutWorker 每 2 秒拉一次 PAYING 的结算单
  List<Item> batch = items.pending(run.id(), 500); // 按 user_id 升序
  tx(() -> {
    BigDecimal batchFee = ZERO;
    for (Item it : batch) {
      if (items.casDone(it.id()) == 0) continue;   // 别的实例已做
      String biz = "SETTLE:" + it.id();
      ledger.apply(it.userId(), BET_LOCKED, it.stake().negate(), it.win() ? BET_SETTLE : BET_LOST, biz, run.marketId());
      if (it.win()) {
        ledger.apply(it.userId(), AVAILABLE, it.stake().add(it.gross()), PAYOUT, biz, run.marketId());
        ledger.apply(it.userId(), AVAILABLE, it.fee().negate(), FEE, biz, run.marketId());
        batchFee = batchFee.add(it.fee());
      }
      notify.toUser(it.userId(), it.win() ? "SETTLE_WON" : "SETTLE_LOST", vars(it, run));
    }
    platform.apply(PLATFORM_REVENUE, batchFee, FEE_INCOME, "SETTLE_BATCH:" + run.id() + ":" + firstId(batch), run.marketId());
  });
}

void finish(SettleRun run) {
  tx(() -> {
    require(items.countPending(run.id()) == 0);
    platform.apply(PLATFORM_REVENUE, run.dust(), SETTLE_DUST, "SETTLE_RUN:" + run.id(), run.marketId());
    require(ledgerQuery.marketConservation(run.marketId()).equals(run.poolTotal()));  // 按账本复核
    marketApi.casStatus(run.marketId(), currentStatus, SETTLED);
    runs.casStatus(run.id(), PAYING, DONE);
  });
}
```

- `require` 失败会让本次事务回滚、结算单标 `ABNORMAL`、告警，钱停在那一步（已派的不回滚，因为每一笔都已在明细里，人工核对后可以继续）。
- 取消、作废的**全额退款**走同样的三段（`kind = REFUND`，每个有效下注退 b，不收费）。
- **结算期间改费率被拒**：`FeeService` 改费率时检查 `settle_phase = NONE`（需求 3.8 第 3 条"结算开始后不能改"）。
- 客户端在 `settle_phase = PAYING` 时显示"结算中"（几秒钟），见 X-2。

**性能（NF-03：10,000 个持仓 ≤ 60 秒；加密市场窗口结束 3 分钟内结算完）**【推断，AC-71 压测验证】：计算段 10,000 行内存计算 + 批量插入约 1～2 秒；派彩 20 批，每批 500 个持仓 × 约 4 条语句（批量执行）约 0.5～1 秒，合计 10～20 秒。加密市场：窗口结束 + 60 秒取 K 线（需求 3.7），取价成功后几秒内结算完，3 分钟有余量。

### 4.4 守恒校验和彩池对账
三个时点都校验：
1. **结算计算时**（上面第 ① 段）：不通过不派彩，市场停在"结算异常"（需求 3.5）。
2. **结算收尾时**（第 ③ 段）：按账本 `ref_market_id` 合计复核：Σ客户 `bet_locked` 减少 = T，Σ(PAYOUT − FEE) + Σ平台(FEE_INCOME + SETTLE_DUST) = T。
3. **每天 UTC 00:30 彩池对账**（`settle/recon/PoolReconJob`，需求 3.9）：未结算市场检查 Σ有效下注 = Σ`pool_option_total.amount` = 账本里这个市场的 BET_LOCK − REFUND；已结算市场检查守恒。不一致写 `settle_pool_recon_issue`、邮件告警财务和超管；有未处理差异时提现自动审批 R12 不通过（AC-38）。

## 5. 状态机实现

### 5.1 状态和允许的跳转
状态（`MarketStatus`）：`DRAFT` 草稿、`LISTED` 已上架、`PAUSED` 已暂停、`CLOSED` 截止下注、`PENDING_RESOLUTION` 待裁决、`PUBLICIZING` 公示中、`DISPUTED` 争议中、`SETTLED` 已结算、`CANCELLED` 已取消、`VOIDED` 已作废。

`MarketStateMachine.ALLOWED`（只有这些边，其余一律抛 `ILLEGAL_TRANSITION`，AC-10）：

| # | 从 → 到 | 谁触发 | 权限 / 条件 |
|---|---|---|---|
| 1 | DRAFT → LISTED | 上架接口；加密自动生成 | `market:publish` + 勾选检查清单；自动生成要求模板已检查 |
| 2 | LISTED → PAUSED | 暂停 | `market:pause`（高危） |
| 3 | PAUSED → LISTED | 恢复 | `market:pause` |
| 4 | LISTED → CLOSED | 截止任务 | `now ≥ close_at` |
| 5 | PAUSED → CLOSED | 截止任务 | 同上（需求 3.2 第 2 条） |
| 6 | LISTED → CANCELLED | 取消 | `market:cancel`（高危），退款 |
| 7 | PAUSED → CANCELLED | 取消 | 同上 |
| 8 | CLOSED → VOIDED | 截止任务 | 有效选项 < 2（E3、E4），退款 |
| 9 | CLOSED → PENDING_RESOLUTION | 事件结束任务 | `now ≥ event_end_at` |
| 10 | PENDING_RESOLUTION → SETTLED | 自动裁决成功 | 经结算三段 |
| 11 | PENDING_RESOLUTION → PUBLICIZING | 确认结果 | `resolve:confirm`（高危） |
| 12 | PUBLICIZING → SETTLED | 公示期满任务 | 窗口到期且没有争议 |
| 13 | PUBLICIZING → DISPUTED | 客户提交争议 | 有下注、窗口内、每人一次 |
| 14 | DISPUTED → SETTLED | 处理争议（维持 / 改判） | `dispute:handle`（高危） |
| 15 | PENDING_RESOLUTION / PUBLICIZING / DISPUTED → VOIDED | 作废 | `resolve:void` 或 `dispute:handle`；系统（E1、E6 超 48 小时、E10 无法判定） |

（第 15 行是 3 条边，合计 17 条边；E1 没人押赢方在结算计算时发现，按第 15 行作废。）

- **实现**：每次跳转是一条条件更新 `UPDATE market_question SET status=:to, version=version+1, … WHERE id=:id AND status=:from`，同一事务写 `market_status_log`；更新 0 行 = 别人已经改过 → 返回"状态已变化"，不重复执行后续动作。所以重复触发、多实例同时触发都是安全的。
- 进入 SETTLED 只在结算第 ③ 段；进入 CANCELLED、VOIDED 时同一事务建退款单（`settle_run kind=REFUND`），退款由同一个派彩任务执行。
- 题目、选项、截止时间、裁决来源上架后不能改：Mapper 的更新语句带 `AND status='DRAFT'`；截止时间只能**提前**的单独接口 `advanceClose`（需求 3.2 第 4 条），提前后新截止时间之后收到的下注由 E14 同样的逻辑退回。

- **服务停机后恢复**（NF-05）：所有任务按"条件已满足"扫描，不按"到点触发一次"，停机期间到期的市场在恢复后第一轮处理；截止时间之后不可能收到下注（判定只看 `receivedAt`）。
- 截止任务的"共享锁屏障"：截止任务在排他锁下读奖池，所有在它之前开始的下注都已提交；之后进来的下注拿到共享锁时状态已是 CLOSED。代价是：极少数在 `close_at` 之前收到、但因为排队在截止任务之后才拿到锁的下注会被拒绝（需要排队超过截止任务的 5 秒周期，正常 p99 下不会发生）【推断】。

### 5.3 多实例时任务不重复
第一期**单实例**部署（沿用 falconx-lite 的取舍，AQ-11），但代码按多实例写：
1. **租约**：`common_job_lease`：任务开始前 `UPDATE common_job_lease SET owner=:me, lease_until=now+30s WHERE name=:job AND (lease_until < now OR owner=:me)`，更新到 1 行才执行；运行中每 10 秒续约。实例异常退出后最多 30 秒由别的实例接手。不引入 ShedLock 依赖（它对 Spring Boot 4 的支持【未核实】，自己写约 60 行）。
2. **条件更新**：即使租约失效（例如 GC 停顿超过 30 秒）两个实例同时跑，状态跳转、结算明细、账本都有条件更新或唯一键，重复执行没有效果（第 4.3、5.1 节）。
3. 推送多实例时经 Redis 发布 / 订阅广播"某市场奖池变化"（第 7 节）；单实例时走内存。
4. `FC_ID_NODE`（雪花节点号）多实例时必须不同（沿用 falconx-lite 约定 25）。

### 6.5 独立抓取程序 fc-scraper（备用方案，AQ-7 / AQ-18，v1.2）

只在免费接口覆盖不到、又必须自动裁决的赛事上用。**主应用不依赖它**：它挂了、被封了，只是少一个来源，结果转人工。

| 项 | 设计 |
|---|---|
| 形态 | 独立目录 `scraper/`、独立镜像 `forecast-scraper`、独立容器 `fc-scraper`；Java 25（和后端同一套工具链），不用 Spring，JDK `HttpClient` + jsoup；有自己的版本号和健康检查 `/healthz`。随同一个 compose 发布，但能单独重启、单独回滚【推断】 |
| 和主应用怎么交换数据 | **主应用拉取**：`GET /v1/results?sport=football&league=<代码>&date=<日期>` 返回统一格式 `{fixtures:[{ref, home, away, kickoffAt, status, homeScore, awayScore, duration, sourceUrl, fetchedAt, rawSha256, extractedBy, evidence}]}`（`extractedBy` 是 `RULE` 或 `LLM`）。只监听容器内网，不对外开端口。主应用按普通数据源处理：超时、重试、熔断、存档（第 6.3 节），原文由主应用存进 `resolve_source_fetch`。不用消息队列：数据量小（每天几十场），拉取最简单，也不用为队列再加一个容器【推断】 |
| 抓哪些站点 | **只抓白名单**（配置文件 `scraper/sites.yml`，新增站点要写明 robots 和条款的检查结果，交 Amos 确认）。候选：**维基百科**（MediaWiki API，赛季页面的比分表）：接口规范要求带联系方式的 User-Agent、请求串行不并发、后台任务带 `maxlag`【证实：[API:Etiquette](https://www.mediawiki.org/wiki/API:Etiquette)】；内容由志愿者更新，**及时性不稳定**，只适合"比赛结束几小时后"的核对。各联赛官网：条款各不相同，**逐个查过才能加**【未核实】 |
| 不抓的站点 | ESPN（迪士尼条款禁止自动访问和商用）、NBA.com（禁止用于博彩）、Sofascore / FlashScore 一类比分站（条款普遍禁止抓取，并有反爬）【推断：后两类没有逐个打开条款】 |
| 礼貌抓取 | 先读并遵守 `robots.txt`；每个站点同时只有 1 个请求，两次之间至少 5 秒；User-Agent 写项目名和联系邮箱（邮箱问 Amos）；只抓需要的页面；条件请求（`If-Modified-Since`）减少流量；收到 429 / 403 立即停这个站点 1 小时并告警 |

| 存档 | 抓到的原文按 sha256 存在抓取程序自己的数据卷，保留 30 天；主应用存档里记录 `rawSha256` 和来源地址，争议时可以对照 |
| 资源 | 内存上限 320 MB（第 11.3 节）；不连主应用的数据库，不持有任何资金相关的密钥 |
| 什么时候建 | **AQ-18 已定（v1.3）：第一期不建**；S8 接入免费源、统计一个月以后，自动裁决成功率低于 90% 或需要免费源覆盖不到的联赛时再建；不建时 `FC_SRC_SCRAPER_ENABLED=false`，主应用里只有一个关着的适配器 |

### 6.6 Gemini 用在哪里（AQ-7，v1.2）

| 用途 | 做法 | 不做什么 |
|---|---|---|
| ①解析不规整的页面 | 抓取程序先用规则（CSS 选择器、表格解析）提取；**规则失败**时，把去掉脚本和样式后的页面正文（截到约 8,000 字符）发给 Gemini，要求按固定 JSON 结构返回比分、状态，并**附上原文里的那一句**（`evidence`）；抓取程序检查这一句确实出现在原文里，不在就丢弃（防止模型编造）。结果标 `extractedBy=LLM` | 不让 Gemini 自己上网搜（Google 搜索接地要另收费，结果也无法核对） |
| ②从新闻里提取比分 | 不做。新闻稿常有错，来源也难以固定 | — |
| ③给裁决员写核对摘要 | 两源不一致转人工时，可以让 Gemini 把两份原文的差异写成一两句话，显示在裁决台上，**只是参考** | 不替裁决员下结论 |
| 结算规则 | **只由 Gemini 解析出来的结果，不能单独构成"两个来源"里的一个**：自动结算要求至少一个来源是结构化接口（football-data / balldontlie / TheSportsDB），并且和它一致；两源都来自 LLM 解析时一律转人工 | — |

- **AQ-19 已定（v1.3）：免费档**。和自动化程序共用一个 key 和一个每天上限：EQ-5 已定"免费档、每天最多 300 次（和体育抓取共用）"，比分解析优先（自动化需求 EX-4）；`FC_GEMINI_DAILY_LIMIT` 是**两边合计**的上限，默认 300（v1.2 写的 200 只算了抓取程序）。
- **密钥**：变量名 `FC_GEMINI_API_KEY`，**Amos 自己填进服务器 `.env`，只给用到它的容器**（抓取程序、自动化程序；compose 里只把这一个变量传给它们，主应用不拿），不经过 AI、不进仓库、不进日志；模型名 `FC_GEMINI_MODEL`，默认 `gemini-2.5-flash-lite`（最便宜，模型下线时改这个变量）。
- **免费额度和费用**：Gemini 2.5 Flash-Lite、2.5 Flash 在免费档"输入、输出免费"；付费档 Flash-Lite 每百万 token 输入 $0.10、输出 $0.40，Flash 输入 $0.30、输出 $2.50【证实：[Gemini 定价](https://ai.google.dev/gemini-api/docs/pricing)】。免费档每天能调用多少次，官方页面不列，要在 AI Studio 里看自己项目的额度；限额按项目算，不按 key 算【证实：[rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)】。**免费档的输入会被 Google 用来改进产品，付费档不会**【证实：定价页"Used to improve our products"一栏】；本项目只发公开网页内容，不发任何客户数据，所以可以用免费档（AQ-19）。
- **用量估算**【推断】：只在规则解析失败、或两源不一致时调用，每天估计 ≤ 50 次；每次输入约 3,000 token、输出约 300 token。按付费价算：Flash-Lite 约 50 ×（3,000 × 0.10 + 300 × 0.40）/ 1,000,000 ≈ **$0.02/天，约 $0.6/月**；用 2.5 Flash 约 $3/月。免费档够用时为 0。
- **降级**：没配 key、超时、额度用完、返回格式不对、`evidence` 对不上 → 这一条结果作废，这个来源当作"取不到"，比赛转人工；告警 `alerts.scraper.gemini`（同一天只发一次）。

## 7. 实时推送

**选 WebSocket，沿用 falconx-lite**（`/api/ws/trading` 和 `/api/ws/market` 的握手限流、断线重连后重拉、Nginx 配置都已在测试环境验证过）。SSE 在单向推送上更简单，但要重新写 Nginx 配置、断线逻辑和测试，而且客户端已有的 `ws.ts`、`useServerEvent` 可以直接用【推断】。

| 通道 | 内容 | 做法 |
|---|---|---|
| `WS /api/ws/user`（登录后） | 本人的余额、通知、充值、提现、结算结果 | 沿用 `UserEventsApi`：事务提交后推送；连上时（含重连）客户端重新拉取账户和未读数（falconx-lite 已踩过"连上前的变化漏掉"的坑） |
| `WS /api/ws/markets` | 订阅 `market:{publicNo}`，收到 `{options:[{no, amount, pct, mult}], total, bettors, ts}` | 下注事务提交后只把市场标"有变化"；`PoolPush` **每秒最多推一次**最新快照（合并），满足"2 秒内"（AC-17）；数字由前端直接替换，不做闪色（C84） |

**高峰并发估算**【推断，交付前压测】：

| 假设 | 数值 |
|---|---|
| 同时在线（WebSocket 连接） | 3,000（第一期上线后数月的高估） |
| 同时在看的市场 | 100 个，平均每个 30 人；热门市场 1,000 人 |
| 推送频率 | 每个市场最多 1 次/秒 |
| 消息大小 | 约 300 字节（10 个选项以内） |
| 推送量 | 平常 3,000 条/秒、约 0.9 MB/秒（约 7 Mbit/秒）；热门市场单个 1,000 条/秒 |

- 新手引导沿用 `Onboarding` + `useOnboarding`：首次登录 4 步（这里押什么 → 赔率怎么算、只对盈利抽成 → 认证 → 充值），终点在充值页；可跳过，"我的"里能重看；"看过"记在 `fc.onboarding.v1:<用户号>`（AC-54）。
- 不闪动：不渲染跑马灯、滚动的最新下注；赔率更新只换数字，没有颜色过渡动画。e2e 检查市场列表、详情、下注页面的计算样式里没有 `animation-name`（除了加载中的转圈）（AC-55）。

### 9.5 原型
架构审核通过后做高保真原型（总则 4.5），沿用复制源的 mock 模式（`VITE_API_MODE=mock`、原型横幅、场景面板）。**v1.2（AQ-12）：原型不部署**，Amos 原话"做完直接发我截图看"：在本地用 `bash scripts/build-prototype.sh` 构建，Playwright 按电脑（1366×768）和手机（390×844）、浅色和深色逐页截图，截图放进 `assets/v1/prototype/` 并在原型说明里列出，交给 Amos；不建 Vercel 项目，也就没有对外地址需要保护；包含空状态（没有市场、没有下注）、奖池为 0、单选项有人押等场景（C32）。原型前先按 Amos 选定的风格方向用 HTML/CSS 画关键页面效果图（市场列表、详情 + 下注、我的下注、裁决台；电脑和手机）。

### 11.0 Cloudflare 能做什么、不能做什么（AQ-1、AQ-2）

本项目的特点：Java 25 Spring Boot 常驻进程、WebSocket、定时任务（每 2～15 秒）、MySQL 行锁事务、热钱包签名、Redis。2026-10-25 打开 Cloudflare 开发者文档逐项核对：

| 服务 | 官方文档怎么说 | 本项目能不能用 |
|---|---|---|
| **Workers** | Free 套餐每次请求 CPU 时间 10 毫秒、Paid 默认 30 秒；内存每个实例 128 MB【证实：[limits](https://developers.cloudflare.com/workers/platform/limits/)】。支持 JavaScript、TypeScript、Python、Rust，其他语言要编译成 WebAssembly；页面没有提到 Java / JVM【证实：[languages](https://developers.cloudflare.com/workers/languages/)】 | **不能跑后端**：跑不了 JVM，内存 128 MB 也放不下 Spring Boot；改写成 JS 等于重写整个后端 |
| **Containers** | 只在 Workers Paid 套餐（每月至少 $5）提供；免费套餐的内存、CPU、磁盘额度都是"N/A"；按实际运行时间每 10 毫秒计费，Paid 每月含 25 GiB·小时内存、375 vCPU·分钟、200 GB·小时磁盘，超出内存 $0.0000025/GiB·秒、CPU $0.000020/vCPU·秒；实例规格最大 4 vCPU、12 GiB【证实：[pricing](https://developers.cloudflare.com/containers/pricing/)、[overview](https://developers.cloudflare.com/containers/)】。**磁盘默认是临时的**，休眠后再启动是全新的磁盘；默认 10 分钟没有请求就休眠；所有请求都要经过一个 Worker 转进来；最终用户不能直接用非 HTTP 的 TCP 连接【证实：[platform details](https://developers.cloudflare.com/containers/platform-details/)】。"不保证任何实例运行多长时间"，主机会不定期重启（先发 SIGTERM，最多等 15 分钟）【证实：[FAQ](https://developers.cloudflare.com/containers/faq/)】 | **不适合**：①不免费；②磁盘不持久，MySQL 放不进去；③后端要常驻（每 2 秒的派彩任务、扫块、WebSocket），按 6 GiB 规格（standard-2）全月常驻估算：内存约 $39 + CPU（按平均 0.3 核）约 $15 + 磁盘约 $2 + 套餐 $5 ≈ **每月 $60**【推断：按上面的单价计算】，比一台云服务器贵；④热钱包私钥放在随时会被换主机的实例里，管理更难 |
| **D1**（数据库） | SQLite；免费每个库最大 500 MB、每天读 500 万行、写 10 万行【证实：[limits](https://developers.cloudflare.com/d1/platform/limits/)、[pricing](https://developers.cloudflare.com/d1/platform/pricing/)】。"每个 D1 数据库本质上是单线程的，一次处理一个查询"【证实：limits】。多条语句只能用 `batch()` 一次提交；导入数据时要求删掉 `BEGIN TRANSACTION` 和 `COMMIT`，否则报"不能在事务里再开事务"【证实：[Worker API](https://developers.cloudflare.com/d1/worker-api/d1-database/)、[import](https://developers.cloudflare.com/d1/best-practices/import-export-data/)】 | **不能承载资金账本**：本项目的下注、派彩、提现都是"先锁行、读余额、判断、再改"的交互式事务（第 4.2 节），D1 没有 `SELECT … FOR UPDATE`、不能在事务中途根据读到的值做判断；免费档每天只能写 10 万行，按每笔下注约 8 行写入，一天约 1.2 万笔就到顶【推断】；而且只能从 Worker 里访问，Java 后端连不上 |
| Durable Objects（SQLite） | 免费套餐可用，每天 10 万次请求、写 10 万行、共 5 GB【证实：[pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)】 | 同样只能用 JS / Wasm 写，等于重写账本；不考虑 |
| **Hyperdrive** | "加速你对**已有**数据库的查询"，支持 Postgres 和 MySQL，免费和付费都可用【证实：[Hyperdrive](https://developers.cloudflare.com/hyperdrive/)】 | 它不提供数据库，只是给 Worker 连外部数据库用的连接池；本项目后端不在 Worker 里，用不上 |
| **R2**（对象存储） | 免费每月 10 GB·月存储、100 万次写类操作、1,000 万次读类操作，**流出流量免费**；超出 $0.015/GB·月【证实：[pricing](https://developers.cloudflare.com/r2/pricing/)】。API Token 可以只授权到指定存储桶的"Object Read & Write"【证实：[tokens](https://developers.cloudflare.com/r2/api/tokens/)】；有"存储桶锁"，在指定期限内禁止删除和覆盖对象【证实：[bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/)】；生命周期规则可以按天数自动删除【证实：[lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)】。开通 R2 必须绑定付款方式（超出免费额度会扣费）【二手：[R2 get started](https://developers.cloudflare.com/r2/get-started/) 写要完成订阅流程，社区回答说必须绑卡】 | **用**：①数据库每日加密备份和 binlog（11.6）；②生产的证件照片、裁决截图（代替 v1.1 的 OSS） |
| **Pages / Workers 静态资源** | Workers 静态资源"请求免费且不限次数"，免费套餐每个版本最多 2 万个文件、单个文件 25 MiB【证实：[billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)、[limits](https://developers.cloudflare.com/workers/platform/limits/#static-assets)】；Pages 免费每月 500 次构建、2 万个文件【证实：[Pages limits](https://developers.cloudflare.com/pages/platform/limits/)】 | **能放，但本项目不迁过去**（研发判断，见下面"前端放哪里"） |
| **CDN、DNS、TLS** | 免费套餐提供"免费 SSL、CDN、DDoS 防护"【证实：[Free plan](https://www.cloudflare.com/plans/free/)】；默认**不缓存 HTML 和 JSON**，按扩展名缓存 JS、CSS、图片等，免费套餐单个文件最大 512 MB【证实：[default cache](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/)】；源站证书（Origin CA）免费，可以配 Full (strict)【证实：[Origin CA](https://developers.cloudflare.com/ssl/origin-configuration/origin-ca/)】；回源认证（Authenticated Origin Pulls）免费可用【证实：[AOP](https://developers.cloudflare.com/ssl/origin-configuration/authenticated-origin-pull/)】；代理等源站响应最多 125 秒，只有 Enterprise 能改【证实：[524](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/)】 | **用** |
| **WAF** | 免费套餐只有"Cloudflare Free Managed Ruleset"（完整的托管规则、OWASP 规则要付费）【证实：[managed rules](https://developers.cloudflare.com/waf/managed-rules/)】；自定义规则 5 条【证实：[custom rules](https://developers.cloudflare.com/waf/custom-rules/)】；限流规则 1 条，只能按 IP、10 秒周期【证实：[rate limiting](https://developers.cloudflare.com/waf/rate-limiting-rules/)】 | **用**：免费托管规则打开；自定义规则用于挡后台域名以外的 `/api/admin`（和 Nginx 的拦截重复一层）；限流仍以 Nginx 和后端的三层为主（第 13 节） |
| **Access**（Zero Trust） | 免费档最多 50 个用户【二手：Cloudflare 官网 Zero Trust 和 Access 页面的搜索摘要，[Access](https://www.cloudflare.com/zero-trust/products/access/)】 | **可以用来保护后台域名**（AQ-20） |
| WebSocket | 所有套餐都支持；空闲会被关闭；Cloudflare 发布新代码时会断开连接【证实：[WebSockets](https://developers.cloudflare.com/network/websockets/)】 | **能用**，要加心跳、靠客户端重连（第 7 节） |
| 中国大陆 | 中国网络只对 Enterprise 客户、并且每个主域名要有 ICP 备案【证实：[China Network](https://developers.cloudflare.com/china-network/)】 | 大陆用户走境外节点，速度在测试环境验收时由 Amos 实测（《Cloudflare》K8 的做法） |

**结论**：
- **AQ-1**：Cloudflare 的免费服务**跑不了本项目的后端**；付费的 Containers 能跑 Java，但磁盘不持久、不保证常驻、估算每月约 $60，比云服务器贵，也放不了数据库。推荐"**一台云服务器跑后端、MySQL、Redis（都在容器里）+ Cloudflare 免费的 DNS / CDN / TLS / WAF 在前面 + R2 免费额度存每日加密备份和生产文件**"（AQ-15 请 Amos 确认）。
- **AQ-2：Cloudflare 免费服务里没有能用的数据库。** D1 是单线程的 SQLite，没有交互式事务和行锁，只能从 Worker 访问；Hyperdrive 只连外部数据库。推荐用**容器 MySQL + 每日自动加密备份到 R2（免费）+ binlog 每 15 分钟上传 + 恢复演练**，代替付费的 RDS（AQ-16 请 Amos 确认，因为这偏离《云服务器》H6"生产用托管数据库"的默认）。
- **前端放哪里**：不迁到 Pages / Workers 静态资源，继续由服务器上的 Nginx 出，Cloudflare 代理在边缘缓存 JS、CSS、图片。理由【推断】：①开了代理以后，带扩展名的静态文件本来就由 Cloudflare 缓存，首屏速度差别不大；②客户端和 `/api` 在同一个域名下（Cookie 不设 Domain、`CrossSiteGuard` 只认本站，第 15 节），拆开要么跨域，要么让 Worker 转发 `/api`（Worker 的调用会计入免费额度，每次请求 CPU 只有 10 毫秒）；③前端和后端用同一个镜像标签发布、一起回滚，部署形态的端到端测试（`e2e-deployed`）也覆盖 Nginx；拆开后要在 GitHub 里存 Cloudflare 的部署 Token，多一条发布线。**以后**官网（`web/site`，纯静态、没有登录）可以单独放到 Workers 静态资源上，不影响其他部分。

### 11.6 备份和恢复（AQ-2 / AQ-16，按《云服务器》H4、H6 补充）

生产不用托管数据库以后，"数据能找回"完全靠下面这套做法。原则：备份要**离开这台服务器**、**服务器被攻破也删不掉、看不到**、**定期真的恢复一次**。

| 数据 | 测试 | 生产 |
|---|---|---|
| MySQL 全量 | 每天 UTC 19:30 + 每次更新前（沿用 `backup.sh`），本机保留 7 天；每天也上传 R2 测试桶 | 同样的时间，本机保留 3 天；**每天上传 R2 生产备份桶，保留 35 天** |
| MySQL binlog | 不做 | 开启 binlog（`binlog_format=ROW`，本机保留 3 天）；**每 15 分钟把新写完的 binlog 文件上传 R2**，保留 35 天 → 最多丢 15 分钟的数据（RPO ≤ 15 分钟） |
| 文件（证件、截图） | 本机目录，随数据库备份一起打包 | 在 R2 私有桶里；存储桶锁：上传后 365 天内不能删除和覆盖（证件只增不改） |
| 服务器 `.env` | 由 Amos 自己保存在密码管理器 | 同左 |
| 镜像 | 保留最近 10 个版本 | 同左 |

**怎样保证备份安全**：
1. **先加密再上传**：用 `age` 的**公钥**加密（`FC_BACKUP_AGE_RECIPIENT`，公钥不是秘密）；**私钥只由 Amos 离线保存**（例如密码管理器 + 一份纸质），服务器上没有私钥 → 服务器被攻破，攻击者也解不开 R2 上的历史备份；Cloudflare 账号出问题，备份内容也不会泄露。
2. **服务器只能写一个桶**：R2 API Token 由 Amos 创建，只授权"生产备份桶"的 Object Read & Write（R2 没有"只能写"的权限）；所以再加**存储桶锁 35 天**：35 天内任何人（包括拿到这个 Token 的人）都删不掉、覆盖不了备份；生命周期规则 36 天后自动删除。
3. **备份失败要知道**：`backup.sh` 每次成功后写一个时间戳；后端的告警检查（沿用 `alerts`）发现"最近一次成功上传超过 26 小时"或"binlog 上传落后超过 1 小时"时发邮件给 `FC_ALERT_EMAILS`。
4. 上传工具用 `rclone`（单个文件、支持 S3 兼容接口），由 `server-setup.sh` 安装；凭据放 `.env`，不进命令行参数和日志。

**恢复演练**（上线前一次，之后每季度一次，结果写进部署方案）：
1. Amos 在测试服务器（或临时开一台按量计费的机器）上提供 `age` 私钥（`nano` 新建文件，演练完删除；**不要发给任何对话框，包括控制台助手**，《云服务器》第三节）。
2. 从 R2 下载最近一份全量 + 之后的 binlog，解密，恢复到一个新的 MySQL 容器，用 `mysqlbinlog` 回放到指定时间点。
3. 在恢复出来的库上跑彩池对账和账本不变量（第 4.4 节、`ledger` 的不变量测试同样的 SQL），核对行数、最近一笔下注和提现的时间。
4. 记录用时（目标：RTO ≤ 2 小时【推断】）和结果；失败就修脚本，再演练一次，**演练没通过不上线**。

**和托管 RDS 比少了什么**（AQ-16，v1.3 Amos 按建议接受）：没有主备自动切换，服务器宕机期间整个服务不可用，恢复要人工按上面的步骤做（约 1～2 小时）；数据最多丢 15 分钟（链上的充值能靠重新扫块补回，下注和提现记录可能要人工核对）。换来的是每月少 $80～160（v1.1 的 RDS 估算）。上线后用户和资金量上来了，再换托管数据库：迁移只要导出导入，代码不用改。

彩池、账本、裁决记录永久保留（NF-09），不做按时间清理（备份的保留期只是"副本"的保留期）。

**R2 用量估算**【推断】：上线初期数据库压缩后 < 200 MB，35 份全量约 7 GB + binlog 约 1 GB → 接近免费的 10 GB·月；超出部分 $0.015/GB·月，多 10 GB 也只是每月 $0.15。上传次数每月约 3,000 次（binlog 每 15 分钟一次），远低于 100 万次。数据量大了以后改成"每周全量 + 每天增量"。

  - **测试环境（v1.3，AQ-23）**：第一次部署时 `fc-test`、`fc-test-admin`、`fc-test-www` 三条 A 记录指向测试服务器、**只开 DNS（灰色云）**，和复制源的子域名一样，因为 Nginx 取真实 IP（下面的 `cloudflare-realip.inc`）在 S12 才做；S12 做完后只给这三个子域名打开代理并加 Access。**这台服务器的云防火墙不能只放行 Cloudflare 的 IP 段**：切回复制源时它的子域名是直连的，会被挡住；测试服务器上只靠 Nginx 的 `geo` 检查和回源认证。生产服务器照下面的做法。
  - **注意 `quickcome.online` 是和复制源共用的 Cloudflare 站点（zone）**：SSL 模式、WAF、回源认证这类设置是**整个站点**的，会影响同一站点下其他**开了代理**的子域名；复制源现在只用 DNS、没开代理（《云服务器》第四节），影响不到它。**AQ-22 已定（v1.3，按建议）**：用 Amos 现有的 Cloudflare 账号；站点级设置改动前，运维先告诉 Amos 会影响哪些子域名；R2 开通时由 Amos 绑付款方式（随 AQ-16）。
  - SSL 模式 **Full (strict)**；源站证书沿用 certbot（Let's Encrypt，HTTP 验证经过 Cloudflare 代理也能完成【推断，S12 实测】）；实测不行就改用免费的 Cloudflare 源站证书（Origin CA）。
  - 打开**回源认证**（Authenticated Origin Pulls，免费）+ Nginx `ssl_verify_client`：只有 Cloudflare 来的连接才能完成 TLS 握手。用 Cloudflare 的全局证书时，别的 Cloudflare 用户理论上也能经 Cloudflare 连到源站【推断】，所以 Nginx 现有的"不认识的域名直接断开"继续保留。
  - 云防火墙 80 / 443 只放行 Cloudflare 公布的 IP 段（现在 IPv4 15 段、另有 IPv6）【证实：[cloudflare.com/ips](https://www.cloudflare.com/ips/)】；阿里云轻量防火墙最多能加多少条规则【未核实】，放不下时只靠下面 Nginx 的检查 + 回源认证。
  - 缓存：Cloudflare 默认不缓存 HTML 和 JSON（接口不会被缓存），带扩展名的 JS、CSS、图片按 Nginx 给的 `Cache-Control` 缓存【证实，11.0】；构建产物文件名带哈希，可以设长缓存；`index.html` 不缓存。
  - 长请求：代理最多等源站 125 秒（免费改不了）【证实，11.0】；本项目没有超过这个时间的接口【推断】，大文件上传（证件）要在这之内完成。
- **Nginx 取真实 IP（开代理后必须改，S12 做）**：现在 Nginx 的 `$remote_addr` 会变成 Cloudflare 的 IP，限流（按 IP）和审计日志里的 IP 全都不对。做法【证实：[Cloudflare 恢复访客 IP](https://developers.cloudflare.com/support/troubleshooting/restoring-visitor-ips/restoring-original-visitor-ips/)，其中写明 IP 段"需要定期更新"】：

```nginx
# deploy/nginx/cloudflare-realip.inc（S12 新增；IP 段由脚本从 https://www.cloudflare.com/ips-v4 和 ips-v6 生成，
# 生成结果提交进仓库，每月由运维核对一次是否有变化）
set_real_ip_from 173.245.48.0/20;
set_real_ip_from 103.21.244.0/22;
# …… 其余 Cloudflare IPv4、IPv6 段 ……
real_ip_header CF-Connecting-IP;   # 只信 Cloudflare 给的这个头，不用 X-Forwarded-For
real_ip_recursive off;

# 不是从 Cloudflare 来的连接一律断开（防止绕过 CDN 直连源站伪造来源）
geo $realip_remote_addr $from_cloudflare {
    default 0;
    173.245.48.0/20 1;
    # …… 同上 ……
}
# 每个 server 块里：if ($from_cloudflare = 0) { return 444; }
```

  - 之后 `$remote_addr` 就是真实访客 IP：`proxy.inc` 里"用 `$remote_addr` **覆盖** `X-Forwarded-For`"的写法不变（《云服务器》安全基线），Nginx 限流 `limit_req_zone $binary_remote_addr` 也自然按真实 IP 计数。
  - 访问日志加 `$http_cf_ray`（Cloudflare 请求号），排查时能和 Cloudflare 后台对上。
  - Cloudflare 的"Pseudo IPv4"保持关闭；真实 IP 可能是 IPv6，后端存 IP 的列要能放下 45 个字符（S12 核对一次）。
  - 本地和 CI 的部署形态测试没有 Cloudflare：`cloudflare-realip.inc` 只在 `FC_BEHIND_CLOUDFLARE=true` 时包含（默认 false），测试服务器和生产设为 true。
- **后台域名**：生产不加 IP 白名单（AQ-14）；**AQ-20 已定（v1.3，按建议）**：后台域名加 Cloudflare Access（免费 50 人以内），进后台前先用 Amos 指定的邮箱收一次验证码；测试环境在 S12 打开代理后一起加。
- **NF-04 首屏 ≤ 3 秒的测法**：上线测试环境后，用 WebPageTest 之类的公开测速（4G 档）从服务器所在地以外的至少 2 个地区（例如东京、法兰克福）各测 3 次市场列表首屏，取中位数，写进测试报告【推断：具体工具在测试方案里定】。

### 11.8 邮件：Resend（AQ-10，v1.2）

- Amos 已定用 **Resend**（"Resend，到时候发给你"）。**API key 不能经过 AI**：由 **Amos 自己在服务器上用 `nano` 填进 `.env`**，智能体只给出要填的变量名和非密钥的值，不接收、不转发 key。
- 现在的代码用 SMTP 发信（沿用复制源，`FC_MAIL_*`），Resend 的 SMTP：主机 `smtp.resend.com`、端口 587（STARTTLS）或 465（SSL）、用户名 `resend`、**密码就是 API key**【证实：[Resend SMTP](https://resend.com/docs/send-with-smtp)】。所以要填的是：

| 变量 | 值 | 谁填 |
|---|---|---|
| `FC_MAIL_HOST` | `smtp.resend.com` | 运维写在填写说明里 |
| `FC_MAIL_PORT`、`FC_MAIL_SECURITY` | `587`、`STARTTLS` | 同上 |
| `FC_MAIL_USERNAME` | `resend` | 同上 |
| `FC_MAIL_PASSWORD` | **Resend API key**（只给"发送"权限、只限这个发信域名） | **Amos 自己填，不发给 AI** |
| `FC_MAIL_FROM` | 完整发信地址，必须是 Resend 里**已验证的那个子域名**下的地址（复制源踩过的坑） | 运维给出完整地址，Amos 核对 |

  不另加 `FC_RESEND_API_KEY`：SMTP 方式下 key 就是 `FC_MAIL_PASSWORD`，多一个变量反而容易填错地方。以后如果改用 Resend 的 HTTP 接口，再加 `FC_RESEND_API_KEY`（同样只由 Amos 填）。
- **免费档**：每月 3,000 封、**每天 100 封**、3 个域名；Pro $20/月 5 万封【证实：[Resend pricing](https://resend.com/pricing)】。测试环境够用；生产按第 14 节估算每月约 5,000 封，**会超出免费档**，而且注册验证码集中在某一天时会碰到每天 100 封的上限（超过的验证码发不出去）→ **AQ-21 已定（v1.3，按建议）**：测试和上线初期用免费档，**每天超过 70 封时告警**（《Amos 待办》v1.7 的建议值；v1.2 正文写的是 80），Amos 再升 Pro（S9 加告警）。
- 测试和生产用两个不同的 API key、两个不同的发信子域名（NF-11 隔离）；是否用同一个 Resend 账号由 Amos 定（一个账号免费档最多 3 个域名）。

- 进程形态（Java 还是别的）、数据管道、卡片图片怎么生成，在开发自动化程序之前写成单独的技术方案交 Amos。

## 21. 风险和技术债

| 风险 | 影响 | 缓解 |
|---|---|---|
| 生产地区访问币安受限 | 加密自动裁决退化为单源 → 转人工 | 用 `data-api.binance.vision`；选地区后实测；OKX 备、Coinbase 第三源 |
| 体育两个源的比赛编号对不上 | 自动裁决失败多，人工量大 | 生成草稿时人工确认对应；上线后统计自动裁决成功率 |
| 单实例发布时短暂不可用 | 截止前 1 分钟内发布会让部分客户下不了注 | 发布安排在没有加密窗口截止的时刻做不到（每 15 分钟一次），所以**发布要快**（目标 < 60 秒）；客户端自动重连、重拉 |
| 热门市场 WebSocket 扇出 | 带宽 | 合并推送、CDN 承担静态资源、带宽按 20 Mbit/秒以上准备 |
| 复制时遗漏旧品牌或旧配置 | 客户看到 Quick Come / FalconX，或连到旧服务 | 第 1.4 节残留扫描 + CI 品牌检查 + 部署清单核对（AC-73） |

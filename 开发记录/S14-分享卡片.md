## 1. 结论
- **`crypto.spec.ts` 偶发失败的根因找到了，是产品代码的问题，已修**：加密自动裁决的定时任务（每 15 秒）和端到端用例的 `/api/e2e/resolve/tick` 同时跑到同一个市场时，两边都读到"等待取数"，都在事务外去取币安和 OKX、各存一组原始返回，只有一边的条件更新生效（结果和结算只有一次，但存档多了一组、外部接口多打一次）。生产上两个实例（或租约意外过期）同样会发生。改成**取数之前先用条件更新"认领"这一次尝试**，没认领到的不取数；体育自动裁决是同一个写法，一起改了。修复前在后端测试和端到端里都能稳定复现，修复后部署形态端到端连续 6 次全过（第 2 节、第 5 节）。
- **MF-5 分享卡片**：五种卡片——市场卡、开奖卡（含押中的开奖卡）、挑战卡、封盘倒计时卡、周报卡；服务器用 Java2D 画 1200 × 630 的 PNG（Open Graph / X 大图卡片的标准尺寸），三种语言；只有系统里的真实数字，没有任何客户的个人信息，没有诱导收益的措辞（F-12）。客户端在市场详情、下注成功（挑战卡自动弹出，可以关掉）、我的下注（押中的已结算单子，金额默认不显示）、周报加了分享入口：手机调系统分享面板，电脑复制链接、下载图片（另有 Telegram / X 的分享页按钮）。分享链接带 `src=share`、`cmp=card-<种类>`、登录了带分享人 `ref`，计入 MF-1 来源统计、不发任何奖励。

## 2. `crypto.spec.ts` 偶发失败：根因、复现、修法
### 2.1 现象（S13）
部署形态第二次运行时 `crypto.spec.ts` 失败 1 个：后台"裁决依据"的原始返回里 `outcome = ok` 的有 4 行（币安、OKX 各两行），用例期望各一行；市场照常结算、金额正确；第三次重跑通过。S13 怀疑"定时任务和用例的手动触发同时去取数"。

### 2.2 根因（读代码 + 实验确认）
`CryptoResolver.resolveOne` 的顺序是：读进度行（PENDING、版本号 v）→ **在事务外**并行取币安、OKX（网关每次调用都写一行 `resolve_source_fetch`，约定 40）→ 判定 → 条件更新 `PENDING → RESOLVING WHERE version = v`。两个触发同时到时：
1. 两边都读到 PENDING / v（定时任务 `CryptoResolveJob` 和 e2e 的 `/api/e2e/resolve/tick` 不是同一个线程；e2e 的 tick 不经过租约；生产上两个实例的租约只是"尽量不重复"，约定 25）；
2. 两边都去取数，各存一组原始返回（共 4 行）；
3. 只有先到的一边条件更新成功、写裁决记录、结算；后到的返回 `raced`。

所以结果和结算不会重复（三道防重复、条件更新），但**存档多了一组不被任何裁决记录引用的原始返回，外部接口也多调了一次**（生产上会多占币安、OKX 的限频额度）。不是"偶发"，是并发的时机问题：定时任务每 15 秒一次，正好和用例的 tick 重叠时才出现；部署形态的容器更慢、重叠的窗口更大，所以在那里先出现。体育自动裁决（`SportsResolver.resolveGroup`）是同样的写法（先读、事务外取数、后条件更新），也有同样的问题。

### 2.3 稳定复现（修复前，实际执行）
| 实验 | 做法 | 修复前结果 |
|---|---|---|
| 后端测试 | `CryptoResolverTest.定时任务和手动触发同时到_只取一次数_存档只有一组`：替身数据源每个回复放慢 400 毫秒，两个线程用栅栏同时调 `resolveDue()` | 失败：币安存了 2 行（期望 1）；原有的 `同时跑三次只结算一次` 加上存档行数的检查后失败：3 行 |
| 后端测试（体育） | `SportsResolverTest.两个触发同时到_每轮只取一次数_存档不多一组`（同样放慢 400 毫秒、两个线程） | 关掉修复跑：失败（结果是 `raced` + `waiting`，主源多存一行） |
| 端到端（开发形态） | 用修复前的后端（把认领那两行临时去掉打的 jar）跑改过的 `crypto.spec.ts`：替身回复放慢 1.5 秒（e2e 替身新加 `delayMs`）、同时发两个 `/api/e2e/resolve/tick` | 失败：一个 tick 返回 `raced`；库里 `resolve_source_fetch` 这个市场 4 行（币安、OKX 各 2 行）、`resolve_record` 只有 1 条 `AUTO_RESULT`——和 S13 看到的现象完全一样 |

### 2.4 修法（产品代码）
- `ResolveMapper.claim`：`UPDATE resolve_auto_task SET next_attempt_at = 认领期之后, version = version + 1 … WHERE status = 'PENDING' AND version = 读到的版本 AND next_attempt_at <= 现在`。改到 1 行的才去取数，之后的条件更新用新版本号；改到 0 行的返回 `busy`、不取数。
- 认领期 `forecast.resolve.claim-ttl` 默认 2 分钟：一轮取数最长约 27 秒（主备并行，3 次 ×（连接 3 秒 + 读取 5 秒）+ 退避），第三源补位再加一轮约 54 秒；进程在取数中途退出时，2 分钟后下一轮接着取（`认领后进程退出_认领期过了接着取`）。
- 体育同样（`SportsMapper.claim`，`forecast.sports.claim-ttl` 5 分钟：主源、备源先后各一次，每次限频排队最多 30 秒）。
- 已经是"结果定了、正在结算"（RESOLVING）的不取数，重复调结算本身幂等（约定 35），没有改。
- 没有跳过测试、没有加重试；测试反而更严：`crypto.spec.ts` 每次都人为制造并发（替身放慢 1.5 秒 + 同时两个 tick，再加上随时可能到的定时任务），核对原始返回正好两行、没有 `raced`。

### 2.5 修复后（实际执行）

- 端到端开发形态：`crypto.spec.ts` 新库连续 3 次通过；全量第 5 节。

## 3. MF-5 分享卡片
### 3.1 五种卡片
| 卡片 | 谁生成、什么时候 | 内容（全部来自系统） | 人少 / 作废时 |
|---|---|---|---|
| 市场卡 | 任何人在市场详情点"分享"（不登录也行） | 题目、品类、状态；每个选项的概率条、人数、金额、预计赔率（截止后是最终赔率）；奖池、下注人数、抽成比例；截止时间（UTC，中文加北京时间、繁体加 UTC+8）；"概率和预计赔率随奖池变化，已扣抽成，最终以截止时为准""截止时只有一边有人押，全额退款"；数据时间 | 选项超过 4 个时画前 4 个，写"另有 N 个选项" |
| 开奖卡 | 市场已结算 / 已作废 / 已取消时，市场卡自动换成它 | 结果（结果那一行绿色 ✓）、各选项最终的人数 / 金额 / 赔率；奖池、派彩合计、抽成、尾差、下注人数（和开奖记录同一份数字，AC-88）；依据（加密：开始价、结束价、来源；体育：比分、来源；平台裁决：裁决人编号） | 作废 / 取消：原因（系统代码翻译成三语，管理员写的原样）、"已全额退款 X USDT，不收抽成" |
| 挑战卡 | 下注成功后自动弹出（P3，可以关掉），客户点"分享" | 大字"我押了「X」，谁敢押「Y」？"（三个以上选项是"谁敢押别的选项？"）；我押的那一行打 ✓；两边人数、金额；"「Y」方当前预计赔率 ×m（已扣 5% 抽成），最终以截止时的奖池为准"（和需求第 3.4 节同一个数） | 对面 0 人："对面目前 0 人；截止时仍只有一边有人押，全额退款"（AC-87） |
| 押中的开奖卡 | 我的下注 → 已结算 → 押中的单子"分享" | 开奖卡 + 大字"我押中了「X」"；**金额默认不显示**，勾"在卡片上显示我的派彩金额"才加一行"我的派彩 X USDT（已扣抽成）"（AC-86） | — |
| 封盘倒计时卡 | 系统生成（第 6.3 节，F-16 草稿）；这次只有生成，自动发布等 MQ-2 | "距截止 N 分钟"；各选项人数、金额、当前预计赔率；"已扣抽成，最终以截止时为准"；只在可下注、截止前有 | 二选一里一边 0 人："「Y」目前 0 人；截止时仍只有一边有人押，全额退款"（照实发，不因为数字难看就不发） |
| 周报卡 | 周报页"分享" | 结束场数、有效场数、作废或取消、奖池 / 派彩 / 抽成 / 退款 / 尾差合计（和周报页同一份）；作废或取消的原因（最多写 3 种） | 本周写"本周截至现在" |

措辞：只用需求原文和市场策略已有的说法；没有"稳赚、必中、翻倍、胜者瓜分、最后入场、别错过"等（F-12、F-15），`CardTextsTest`（模板）和 `S14CardsTest`（每种卡片三种语言实际生成的文字）都检查；模板里不写数字（数字只能由程序从系统数据填）。

### 3.2 图片怎么生成
| 项 | 做法 |
|---|---|
| 尺寸、格式 | 1200 × 630 PNG（Open Graph、X 的 `summary_large_image` 都按 1.91:1 显示）；每张约 50～90 KB |
| 画法 | `CardPainter`（Java2D，不用浏览器、不用外部服务）：顶部品牌和品类 / 状态 → 大字一句 → 题目（自动折行，中文按字、英文按词，最多 2～3 行，超出加"…"）→ 选项行（概率条）或周报的数字格 → 关键数字 → 规则说明 → 数据时间；放不下时依次减少说明、题目行数 |
| 颜色 | 客户端的设计 token（方向 A 浅色）；蓝色只用于概率；只有加密"涨 / 跌"和押中的结果用绿红（PQ-1、约定 46）；没有闪动元素（C84，图片本来就是静态的） |
| 字体 | 拉丁字母和数字用 DejaVu Sans（镜像自带），中文用文泉驿正黑（`deploy/app.Dockerfile` 装 `fonts-wqy-zenhei`，约 16 MB，简繁都有）；按字符选字体（`CardFonts.runs`）。没有中文字体时健康检查 `alerts` 的 `cards.font` 是 DOWN（不影响 `status`，约定 11） |
| 缓存 | 按内容指纹（种类、语言、全部文字和数字）缓存最近 64 张；数字没变就不重画；同时最多画 2 张，排队超过 5 秒返回 503。HTTP：ETag（304）、进行中的卡片 `max-age=60`、已结束的 / 过完的周 1 小时 |
| 性能（本机实际） | 第一次请求（要画）44～167 毫秒、中位数 61 毫秒，缓存命中中位数 35 毫秒；每张 41～95 KB；部署形态端到端跑完后 app 容器 345～365 MiB（上限 576），第 5.3 节 |

### 3.3 分享链接、Open Graph、来源统计
- 链接：`https://<客户端域名>/m/{市场编号}?src=share&cmp=card-<种类>&ref=<客户编号>&cl=<卡片语言>&card=<凭证>`（周报是 `/results/weekly/{周}?…`）。`ref` 只在登录时带；`card` 只有挑战卡、押中的开奖卡有。`/m/` 由 Nginx 301 到市场详情，参数保留（S13）。
- `cl` 是卡片的语言，只给链接预览选语言（标题、描述、图片），客户端不用它——不会把打开链接的人的界面语言改掉（`?lang=` 会被记住，所以没用它）。
- 页面头部（Nginx SSI 插入，S13）：市场页 `og:image` = 这张卡片（链接里的凭证属于这个市场时用凭证那张，否则市场卡 / 开奖卡），`og:image:width/height/alt`、`twitter:card summary_large_image`、`twitter:image`；挑战卡链接的 `twitter:title` 是卡片上那句大字。周报页用周报卡。规范地址仍是不带参数的地址，分享参数不影响收录。
- `robots.txt` 加 `Allow: /api/public/cards/`（写在 `Disallow: /api/` 前面）：X 的抓取遵守 robots，不放行就不显示图片。
- 来源统计：打开链接的人照常记一次访问（S13 的 `captureAttribution()`），后台"来源统计"按 `src=share`、`cmp`、`ref` 统计；**不给分享人任何奖励**（MQ-5）。端到端核对了"打开挑战卡链接 → 来源统计里这个分享人 1 次访问"。

### 3.4 隐私
- 公开的卡片（市场卡、开奖卡、倒计时卡、周报卡）只用公开数据（详情按"没登录"取）。
- 挑战卡、押中的开奖卡：生成时核对这个客户确实有这个选项的持仓 / 押中了（不能替别人或给没押的选项生成）；表 `market_share` 存客户编号只为去重，**任何公开接口都不返回**；链接和图片地址里只有 22 位随机凭证。押中的开奖卡金额默认不显示。
- 卡片上没有邮箱、姓名；链接里有客户编号（需求原文"分享人 ref（客户编号）"），分享弹窗写明"链接里带你的客户编号，只用于统计来源，不发任何奖励"（SQ-36）。

## 1. 结论
- 新模块 `settle`：**结算三段**（计算 → 派彩 → 收尾）、**三道防重复**（结算单唯一 `(market_id, kind)`、明细 PENDING → DONE 条件更新、账本幂等键）、**可续跑**，按 AQ-3 方案 B 实现（**Amos 2026-10-25 已定：B**，先算好、落结算单，再分批派彩）；**每批持仓数是参数 `forecast.settle.batch-size`（环境变量 `FC_SETTLE_BATCH_SIZE`），默认 500** = 计算一个事务、每批 500 个持仓一个事务、收尾一个事务；**0 = 计算、派彩、收尾在同一个事务里**（需求原文的写法，保留为可配置项）。两种模式都测了守恒、幂等、中途崩溃续跑、AC-23 三次并发、混合死锁。
- 结算计算 `SettleMath`：G 向下取整、F 四舍五入、尾差 D 归平台、**守恒 ΣPay + ΣF + D = T 且 0 ≤ D < 0.01 × 赢方持仓数**；需求第 3.5 节例子在纯计算和真实数据库里（两种模式）**逐分相等**：Alice 66.66 / 3.33 / 163.33、Bob 1,666.66 / 83.33 / 4,083.33、Carol 2,266.66 / 113.33 / 5,553.33，ΣG 3,999.98、ΣF 199.99、ΣPay 9,799.99、D 0.02、平台收入 200.01。固定种子 1,000 个随机市场全部守恒、尾差在范围内、平台不亏。
- **全额退款**：取消（截止前）、作废（E1 没人押赢方、E3 只有一个选项有人押、E4 奖池为 0、E5 人工作废）都在 market 进入终态的同一个事务里建退款单，派法和派彩相同；**E14** 实际开赛早于截止时，之后收到的下注全额退回、其余照常结算；**E15** 员工账户的下注退回；**提前截止**后新截止时间之后收到的下注全额退回（S4 留下的 `onCloseAdvanced`）。退款不收费，同步扣持仓、选项奖池（含定格的奖池）。
- **彩池对账**：结算前检查（Σ有效下注 = Σ选项奖池 = Σ持仓 = 账本下注锁定、定格奖池相等、没有待处理差异）、结算后按账本复核守恒、**每日 UTC 00:30 对账**（`PoolReconJob`，未结算市场 + 近 3 天的结算单）。对不上：**记差异、邮件告警、后台列出、停止派彩、结算单和市场停在"结算异常"**（`settle_phase = ABNORMAL`），处理差异后可在后台重试。提现自动审批 R12 加了"彩池对账没有未处理的差异"（AC-38）。
- **超管手工填结果直接结算**（临时入口，S7 裁决台做好后替换）：`POST /api/admin/markets/{publicNo}/settle`（`resolve:confirm`，高危：原因必填 + 勾选确认，写审计），另有人工作废、结算详情、结算单列表 / 详情 / 重试、对账差异列表 / 处理共 7 个后台接口。
- **通知**：#11 结算赢、#12 结算输、#13 取消作废退款、#14 晚于开赛 / 截止的下注退回，员工告警"结算异常"、"彩池对账有差异"。**文案全部是研发初稿，PM 在 S9 定稿**（第 2.6 节）。同一客户多个持仓合并成一条。
- **10,000 持仓压测（AC-71，两种模式）**：batch-size = 0 结算 **6.08 秒**，期间这些客户的下注、提现最长被卡约 5 秒（p99 4.9 秒）；batch-size = 500 结算 **9.36 秒**，期间下注 p99 0.23 秒、提现 p99 0.52 秒。都远小于 60 秒。数据见第 6 节；AQ-3 已定 B，默认值已改成 500。

### 2.3 规则怎么落到代码
| 规则 | 代码 |
|---|---|
| 需求 3.5：G = ⌊S × L ÷ P_W⌋（0.01）、F = round(G × 费率)、Pay = S + G − F、D = L − ΣG 归平台、守恒 | `SettleMath.settle`；持仓（同一客户同一选项合成一个）只舍入一次 |

## 4. 并发、幂等、续跑的设计和测试
### 4.1 两种事务边界
| | batch-size = 0（可配置项，需求原文的写法） | batch-size = N > 0（默认 500，方案 B，AQ-3 已定） |
|---|---|---|
| 计算 | 一个事务：锁市场 → `lockAll` 锁齐全部下注客户账户 → 对账 → E14 / E15 退回 → 算 → 守恒 → 写结算单和明细 | 同左，但不先锁客户账户 |
| 派彩 | 同一个事务里派完全部明细；平台抽成一笔 | `PayoutWorker` 每批（N 个持仓，补齐到客户边界）一个事务；平台抽成每批一笔 |
| 收尾 | 同一个事务：尾差入平台 → 按账本复核 → 已结算 | 一个事务 |
| 中途崩溃 | 整个回滚，市场还是待裁决，重新触发从头算，结果相同 | 已提交的批不变，续跑只派剩下的，结果和一次跑完相同 |
| 客户看到 | 没有"结算中" | 派彩期间 `settling = true`（X-2） |

### 4.3 实测

### 4.4 修了 S3 的 `MarketService.lock(publicNo)`
原来先按编号普通读（建立了可重复读的快照），再按 id 加锁。加锁读本身读最新，但同一事务后面的普通读（取消时查有效下注、截止提前时查之后的下注、#22 查下注客户）用的是锁之前的快照，**会漏掉锁等待期间刚提交的下注**——这笔下注就不会被退回，钱一直锁在"下注中"，对账会报差异。改成第一句就是加锁读（`lockByPublicNo`）。这是 S5 的取消退款测试里发现的。

## 6. 10,000 持仓结算压测（AC-71，AQ-3 的数据）
- 测试：`backend/src/test/java/com/forecast/app/settle/SettleLoadTest.java`。建 10,000 个客户、一个两选项市场、每人一个持仓（赢方约 4,000），截止、事件结束后结算；结算前 3 秒和结算期间，12 个线程不停地操作同一批客户：8 个在**另一个市场**下注，4 个让其中 40 个客户提交提现再撤销，统计每次的延迟；InnoDB 行锁等待取自 `information_schema.INNODB_METRICS`（`lock_row_lock_waits`、`lock_row_lock_time`，全库）。
- 机器：开发机 4 vCPU、16 GB；应用、MySQL、Redis、压测线程在同一台；连接池 40。

| | batch-size = 0（一个事务） | batch-size = 500（分批） |
|---|---|---|
| 结算耗时 | **6.08 秒**（赢方 4,018） | **9.36 秒**（计算 1.99 + 派彩 7.38，赢方 3,979） |
| 结算前 3 秒：下注 p50 / p99 | 80 / 197 毫秒（最长 248） | 45 / 104 毫秒 |
| 结算前 3 秒：提现 p50 / p99 | 253 / 675 毫秒 | 182 / 271 毫秒 |
| **结算期间：下注** | 149 笔，p50 76、**p99 4,877、最长 5,005 毫秒** | 1,365 笔，p50 48、**p99 227、最长 541 毫秒** |
| **结算期间：提现** | 30 笔，p50 221、**p99 4,991 毫秒** | 243 笔，p50 144、**p99 522、最长 704 毫秒** |
| InnoDB 行锁等待 | 68 次，合计 56,871 毫秒 | 584 次，合计 12,505 毫秒 |
| 对照：不发通知 | 3.97 秒 | 5.97 秒 |
| 对照：通知没有批量（逐个 `toUser`）时 | 22.84 秒 | 29.61 秒 |

- 解读：一个事务模式更快，但整个结算期间锁住全部 10,000 个客户的账户，**这些客户在别的市场的下注、提现要等到结算结束**（约 5 秒，正好是结算的派彩部分），结算期间总共只完成了 149 笔下注；分批模式总耗时多 3 秒，但每批只锁 500 个客户约 0.3 秒，**下注、提现基本不受影响**（p99 227 / 522 毫秒，NF-01 是 500 毫秒）。
- 通知最早占结算时间的 80% 以上（逐个查偏好、逐条插入），改成 `NotifyApi.toUsers` 批量以后从 22.8 秒降到 6.1 秒；账本也改成批量记账（`applyBatch`）。
- 都远小于 AC-71 的 60 秒。正式压测在 S12 的测试环境（绑核、同样的 compose）。

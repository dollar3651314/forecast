## 1. 结论
- **加密市场自动生成**（market 模块 `market/autogen/`）：自动生成模板按**场次**配置——币种（BTC、ETH）、周期（15 分钟 / 1 小时）、生成方式 **SCHEDULE（按场次，节目化，默认）**：`slots` 里每个 UTC 窗口开始时间每天一场，开放前 `generate_ahead_min`（默认 60）分钟生成；**ROLLING（可切换）**：保证未来至少 N 个窗口可下注或待开放（15 分钟默认 4、1 小时默认 3，AC-28）。按模板生成的市场**直接上架**（需求第 4.2 节），开放、截止提前量用参数设置（窗口开始前 30 秒截止；15 分钟提前 60 分钟、1 小时提前 3 小时开放），费率按品类默认值。生成任务每分钟一轮、带租约；同一模板同一窗口只有一个市场（唯一键，4 个线程同时生成也只有一个）。
- **新库默认**：BTC 1 小时、按场次、每天 13:00 UTC 一场（MQ-1），**关闭**——启用前要有 `market:publish` 的人按第 4.1 节清单检查一次（后台详情里看得到按下一个窗口渲染出来的题目、规则、来源、选项和缺的必填项），勾选 `checked` 后启用（SQ-12）。
- **权限**：新建、修改、关闭模板和改规则文本模板要 `market:autogen`（高危，原因必填，审计）；**修改只能在关闭时**、改了要重新检查；启用要 `market:publish`。
- **三个 `CandleSource` 适配器**（`resolve/source/`）：`BinanceSpot`（主）、`OkxSpot`（备，只用 confirm = 1 的 K 线）、`CoinbaseSpot`（第三源，BTC-USD，**默认关闭**，只在主备一方拿不到时补位）。**真实接口冒烟测试**（本机有网，2026-10-25 07:49 UTC）：三个来源对 BTC、ETH 的最近 1 小时和 15 分钟窗口全部返回 200、格式和解析一致、根数齐、方向一致（第 5.2 节）；`api.binance.com` 仍返回 451，`data-api.binance.vision` 正常。
- **数据源网关**（`SourceGateway` + 公共的 `common/http/ExternalHttp`）：连接超时 3 秒、读取超时 5 秒（读完响应体的总时长，慢慢吐字节也算超时）、响应体上限 1 MB；一轮最多 3 次、退避 1 秒、2 秒（不超过 4 秒），只重试超时、连不上、断开、5xx、429、408；连续 5 次失败**熔断** 60 秒，之后半开放 1 次探测；**每次调用（成功、失败、超时）和每次被熔断跳过都存档**（原文、sha256、解析结果、耗时），存档失败当作取数失败；**在数据库事务里调用直接报错**（C81 第 3 条）。熔断打开时健康检查的 `alerts` 里 `source.binance` / `source.okx` 为 DOWN（不影响 `status`）。
- **自动裁决**（`resolve/auto/CryptoResolver`，任务每 15 秒、带租约）：市场进入待裁决时建进度（market 的同一事务）；**窗口结束 1 分钟后**在事务外并行取主源、备源 → 两个来源方向一致（收盘 = 开盘判涨，E9；"正好相等"导致方向不同时以首选为准）→ 记下结果和裁决记录 → 调 S5 的结算（`resolve.api.ResultHandler`，由 settle 实现）→ 已结算。**不一致或拿不到：每分钟重试；30 分钟后转人工**：进度 MANUAL + 裁决记录 AUTO_FAILED（带两个来源的价格和存档行）+ 告警邮件 `RESOLVE_AUTO_FAILED`，市场留在待裁决，S7 的裁决台从这里接手（后台已有"转人工"列表和裁决依据接口）。
- **已结算市场的详情**（客户端 `GET /api/markets/{publicNo}`）新增 `resolution`：结果、开始价、结束价、来源（按首选来源）、参与判定的各来源价格和 sha256（AC-27、需求第 4.3 节）。
- **端到端**（替身数据源）：后端 `CryptoAutoFlowTest`（两种结算事务边界）和 Playwright `e2e/tests/crypto.spec.ts`（两种形态）都走完了"**自动生成 → 下注 → 窗口结束 → 自动裁决 → 自动结算**"。e2e profile 下币安、OKX 的地址指向后端自己的替身 `/api/e2e/candles/**`，走的是真实的适配器、网关、存档和裁决器。
- 迁移：`V14__crypto_autogen_resolve.sql`（5 张表、规则文本模板和默认自动生成模板的初始数据、员工告警模板 1 个）。V1～V13 没有改。
- 本地实际执行：后端全量空库 verify、外部调用测试、端到端两种形态、真实接口冒烟、索引检查、仓库品牌检查、gitleaks，全部通过，详见第 5 节。

## 2. 做了什么
### 2.1 数据（迁移 V14）
| 表 / 数据 | 说明 |
|---|---|
| `market_template` | 规则文本模板：种类（`CRYPTO_UPDOWN`）、名字、三语题目和规则、首选 / 备用来源、选项（`[{outcome: UP / DOWN, label, winCondition}]`）、版本号。文字里可用变量 `{asset}`、`{pair}`、`{okxPair}`、`{date}`、`{startTime}`、`{endTime}`、`{minutes}`、`{closeLeadSeconds}`（`market/autogen/AutogenRender.java`）。初始一个"加密涨跌（币安 K 线）"，规则按需求第 4.3 节的写法（研发初稿，PM 可在后台改） |
| `market_autogen` | 自动生成模板：币种、周期（15M / 1H）、生成方式（SCHEDULE / ROLLING）、场次 `slots`（UTC "HH:mm"）、滚动个数、开放前多久生成、规则文本模板、单客户上限（为空用品类默认）、开关、检查人 / 时间 / 检查的模板版本、版本号。**唯一 (symbol, period)**。初始一个：BTCUSDT、1H、SCHEDULE、`["13:00"]`、关闭 |
| `resolve_source_fetch` | 数据源原始返回存档（**只增不改、永久保留**，NF-09）：市场、来源、第几次尝试、请求地址、HTTP 状态、原文（≤ 1 MB）、**sha256**、结果 OK / NOT_READY / FAILED / CIRCUIT_OPEN、解析结果、错误、时间、耗时 |
| `resolve_record` | 裁决记录（**只增不改**）：S6 写 AUTO_RESULT（结果、依据）、AUTO_FAILED（转人工、两个来源的数据）；S7 起加提议、确认等 |
| `resolve_auto_task` | 每个加密市场的自动裁决进度：PENDING（等待取数）→ RESOLVING（结果已定、正在结算，崩溃后续跑）→ RESOLVED；或 MANUAL（转人工）/ CLOSED（市场已不在待裁决）；次数、下一次时间、转人工的时间、最后原因 |
| 通知模板 `RESOLVE_AUTO_FAILED` | 员工告警（邮件）：市场编号、题目、多少分钟、最后一次的原因。文案研发初稿，PM 在 S9 定稿 |

`market_question` 的 `autogen_id`、唯一键 `uk_market_autogen_window (autogen_id, event_start_at)` 在 S3 的 V9 里已经建好，S6 开始写。

### 2.6 外部调用清单（C81；本步实现的部分，和架构方案第 6.3 节一致）

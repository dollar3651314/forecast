- 先锁一行确定存在的行（客户账户）再普通读请求号，不对可能不存在的行加锁读（约定 34）。

### 1.4 幂等【实际执行】
- 后台每次打开确认框生成一个请求号（`web/admin/src/utils/adjust.ts` 的 `newRequestId`，`[A-Za-z0-9._-]{8,64}`，和追踪号同一个规则）。同一个请求号再提交：返回第一次的结果，`duplicate = true`，余额不变、只有一条流水；同一个请求号换了金额或客户：409 `ADJUST_REQUEST_REUSED`。
- 并发：同一个请求号同时来 8 次，只入一次（`AdminTestCreditTest` 的并发用例：同一客户在账户行锁上排队，第二个一定读到第一个写的单子；不同客户用同一个请求号由唯一键 `uk_ledger_test_credit_req` 挡住）。

### 1.5 对账和报表：单独一行【实际执行】

- 报表（后台"结算 → 报表"）：合计多一张"测试入金"卡片（金额、笔数），按天的表和 CSV 多一列"测试入金"；**不进平台收入，也不冲减补偿支出**（`settle/run/SettleAdmin.report` 经 `ledger.api.AdjustReportApi` 取数）。
- 钱包对账（充值 ↔ 账本 ↔ 链上）只看 `DEPOSIT` 类型，测试入金不会被当成"账本里有入账但没有对应充值"（D-259）。

### 1.6 风控和提现怎么对待测试入金
- **风控：当作充值算**（按主会话的建议，D-260）【实际执行】。`CustomerFlowApi.depositsSince`（账本 `depositsSince` 的 SQL）把 `TEST_CREDIT` 和 `DEPOSIT` 一起算，所以：
  - "充了不玩就提"（`DEPOSIT_NO_BET`）：测试入金后不下注就提现，会告警；
  - 提现自动审批 R8（近 30 天充值后的有效下注）、R9、R10 的"充值"口径都包括测试入金；
  - 下注时的 KYC 阈值（累计充值超过阈值要先认证）也包括测试入金——测试环境入金超过阈值，下注前要先完成 KYC，和真实充值一样。
  - 不包括：充值到账通知（#3 `DEPOSIT_CREDITED`）、充值后的 KYC 提醒邮件（`KycThresholdNotice` 只在链上充值入账时触发）。测试入金不发任何通知（D-261）。
- **提现：允许发起，走完审批流程**【代码走查】。测试入金进的是可用余额，可提金额 = 可用余额，所以能发起提现，冷静期、自动审批、人工审核都照常。链上发出这一步按测试环境现有的行为：配了这条链的热钱包（测试网）就在测试网上发出；没配的链提现停在"已审核待上链"（`wallet/withdraw/WithdrawSenders`："没有广播器的链，提现停在已审核待上链"）。代码没有为测试入金改提现的任何规则。【未验证】测试环境热钱包配了哪些链要看服务器上的 `.env`。

### 2.3 账本【实际执行】
- 新流水类型：客户 `MANUAL_CREDIT`（可用 +）、`MANUAL_DEBIT`（可用 −）；新平台账户"人工调账" `PLATFORM_MANUAL_ADJUST` 的 `MANUAL_ADJUST_OUT`（加款时 −x）、`MANUAL_ADJUST_IN`（扣款时 +x）。平台账户余额 = 累计扣款 − 累计加款，**可正可负**（CHECK 允许）。
- 迁移 `V30__s17b_manual_adjust.sql`：两个 CHECK 加新种类、插入平台账户、调账单 `ledger_adjust`（方向、类别（和方向的组合也有 CHECK）、金额、前后可用余额、参考号、原因、是否超过上限、请求号（唯一）、操作人；**只增不改**）、两个参数、通知模板 `BALANCE_ADJUSTED`（#24）、菜单 `adjustments`、风控扫描进度 `manualCredits`。
- 一个事务（READ COMMITTED，`ledger/adjust/ManualAdjustService`）：锁客户账户行 → 查请求号 → 检查（上限、扣款 ≤ 可用）→ 写调账单 → 客户记账 → 平台记账（最后锁平台账户行）→ 通知 #24（同一事务，回滚就不发，约定 10）→ 提交后推 `account` 事件。
- **扣款**只扣可用余额：现在可用 < 金额时 409 `ADJUST_INSUFFICIENT`（提示现在的可用余额），下注锁定、提现冻结不动；账本层的"不能为负"和数据库 CHECK 兜底（`AdminManualAdjustTest`：有 60 下注锁定时扣 50 被拒、扣 40 成功、下注锁定还是 60）。
- 幂等：后台每次打开确认框生成请求号；同一个请求号再提交返回第一次的结果（`duplicate`），换了客户、方向、类别或金额 409；6 个并发同一请求号只调一次、通知只发一次。
- 改错了只能再做一笔反方向的调整（没有撤销，调账单和账本都只增不改）。

### 2.4 限额：超过单笔上限怎么办（SQ-57）【实际执行】
- 实现的是**建议的做法**：超过上限时确认框里多一个勾选"我确认超过单笔上限（X USDT）"，不勾不能提交（后端 409 `ADJUST_OVER_LIMIT_UNCONFIRMED`）；调账单 `over_limit = 1`、审计里 `overLimit: true`、列表里标"超过上限"。
- 理由：人工调账的真实场景（大额充值没到账）可能超过上限，直接拒绝只会逼人拆成几笔，反而没有记录；再确认一次 + 标记 + 24 小时累计告警，既不挡正常业务，又能事后查。另一个选项"直接拒绝、要先在参数设置里改上限"也容易改（去掉确认参数即可），等 Amos 定。

### 2.5 通知客户（#24）【实际执行】

- 文案检查过禁用的说法（`S9NotifyFlowTest`：编号、渠道、三种语言、变量登记、繁体里没有简体字）。

### 2.7 风控和提现（SQ-58）【实际执行】
- **"充值未到账补入"的人工加款当充值算**：账本记录的来源业务用 `ADJUST_DEPOSIT`（其他类别用 `ADJUST`），`depositsSince` 按它把这类加款算进充值——"充了不玩就提"、提现自动审批 R8～R10、KYC 阈值都包括它（AC-126）。
- **其他类别（建议）**：不算充值，也不算已结算的盈亏（R9、R10、R13 的 `realized` 只看派彩、补偿、本金、抽成）。"误入账扣回"不冲减充值（不知道当初误入的是哪种钱；真实充值被链上回滚用的是系统的冲正 `DEPOSIT_REVERSAL`）。"其他"加款不算充值：它可能是客服补偿之类，不应该让客户少下注就能提现的门槛变松，也不应该触发 KYC。
- **新告警 `MANUAL_CREDIT_LARGE`（SQ-59）**：风控扫描按 id 往后读人工加款（`ManualAdjustApi.creditsAfter`，进度 `manualCredits`），每一笔看这个客户 [这一笔 − 24 小时, 这一笔] 的人工加款合计：含这一笔超过阈值、不含这一笔时没超过 → 记一条告警（ref = 这一笔的调账单），给有 `risk_alert:view` 的人发邮件；同一次越过只告警一次。阈值默认 10,000 USDT（参数设置"风控"一组）。后台"风控告警"页多一个类型"24 小时人工加款过大"。
- 不在调账事务里做风控（约定 52：风控只读别的模块的 api、按 id 扫描）。

## 5. 研发的决定
- **D-257** 测试环境的判断依据用现有的 `FC_ENV_LABEL`（等于 `test`），不新加开关：生产没有这个变量，没有可以误开的配置项；和"测试环境"标识条、邮件标题的"[测试]"同一个来源。
- **D-258** 后台按钮由后端详情接口的 `testCredit`（测试环境才有）决定，不让前端自己读健康检查：按钮显不显示和接口在不在由同一个后端配置决定，不会出现"有按钮、点了 404"。
- **D-259** 测试入金不是充值：不写钱包的充值表，钱包对账只看 `DEPOSIT`，不会报"账本有入账但没有对应充值"；流水类型、客户端流水、报表、对账都单列。
- **D-260** 风控和提现把测试入金当充值（`depositsSince` 加 `TEST_CREDIT`），测试时能走到"充了不玩就提"、R8～R10、KYC 阈值。生产没有测试入金，这条 SQL 对生产没有影响。
- **D-261** 测试入金不发客户通知（不是真实充值，不发"充值已到账"）；只推一个账户变化事件让客户端刷新余额。
- **D-262** 端到端不新加 e2e 专用开关：同一个用例按后端的 `env` 走"测试环境"或"生产形态"两条路，部署形态（和测试环境同样的配置）走第一条，默认形态（和生产同样不设）走第二条。
- **D-263** 客户端流水筛选不加"测试入金"一项（生产不该看到），"全部"里显示。
- **D-264** 人工调账和测试入金都放在 ledger 模块（`ledger/adjust/`，表名 `ledger_*`）：它们是"直接改余额"，只有账本模块能做；不另起一个模块（ArchUnit 的模块表、内容程序的隔离测试都不用改）。
- **D-265** 人工调账的对手方是一个平台账户（`PLATFORM_MANUAL_ADJUST`），加款、扣款都对它记反方向，余额可正可负；不分成"加款账户""扣款账户"两个：对账只看一行就知道净额。
- **D-266** 哪些人工加款当充值，用账本记录的来源业务（`ADJUST_DEPOSIT` / `ADJUST`）区分，`depositsSince` 不用去连调账单。
- **D-267** 查看"人工调账记录"用已有的 `recon:view`，只新加一个高危权限点 `balance:adjust`（调整）：财务对账的人能查能导出，不能调。
- **D-268** 通知 #24 不写操作人和内部原因（原因是给审计看的，可能有内部信息），只写方向、金额、类别、调整后的可用余额。

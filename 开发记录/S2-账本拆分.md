## 1. 结论
- 账户三项改为**可用余额 / 下注锁定 / 提现冻结**（`Bucket`：`AVAILABLE`、`BET_LOCKED`、`WITHDRAW_FROZEN`）；新增**平台收入**、**平台补偿支出**两个账户（补偿支出账户的可用余额可以为负）；按架构方案第 3.2 节定义了下注锁定、结算赢 / 输、派彩、抽成、退款、补偿和平台侧三种流水类型，**每种类型写死"用在哪种账户、改哪一项、只能加还是只能减"**，不符合的记账直接拒绝。下注、结算的业务逻辑没有做（S4、S5）。
- 不变量"任何时刻账本合计 = 余额"：代码上只有一个改金额的地方，并且和账本记录在同一个事务；新加核对接口 `LedgerQueryApi.mismatches()`；用固定种子的**并发随机测试**在真实 MySQL 上验证（8 线程 × 150 次随机业务，含故意的余额不足和重复提交），另外核对 value_after 连续、内部转移净额为 0、幂等键唯一。
- 迁移只加新脚本：`V6__ledger_buckets.sql`（账本）、`V7__withdraw_min_amount.sql`（最小提现 10 → 100）、`V8__brand_quick_come.sql`（通知模板品牌名）。V1～V5 没有改。
- 单笔最小提现默认 100（RQ-16），后台改最小金额或改某条链的手续费时都校验"最小金额 > 每条链的手续费"，不满足时一次列出全部不满足的链。
- 品牌按 Amos 2026-10-25 的口径改成 Quick Come（三个前端、PWA、推送、通知模板）；`scripts/brand-check.json` 里 Quick Come 的检查保持关闭并写明原因；需求说明书升 v1.2、架构方案升 v1.1、《项目地图》约定 17 改写。S1 的 SQ-1 因此关闭（第 7 节）。
- 本地实际执行：后端 313 个测试（新加 17 个），0 失败、2 个跳过（同 S1：真实节点、anvil 没设环境变量）；三个前端 lint、单元测试（130 / 160 / 29 个）、真实和原型构建、旧品牌名检查、模拟层检查全部通过；端到端两种形态通过；索引检查、仓库旧品牌名检查、gitleaks 通过。详见第 5 节。

## 2. 做了什么
### 2.1 账本（`backend/src/main/java/com/forecast/app/ledger/`）
| 内容 | 说明 |
|---|---|
| `api/Bucket` | `BALANCE` 改名 `AVAILABLE`，新增 `BET_LOCKED`（客户端"下注中"） |
| `api/AccountKind`（新） | `USER` / `PLATFORM_REVENUE`（抽成 + 结算尾差）/ `PLATFORM_COMPENSATION`（补偿支出，可用余额可以为负） |
| `api/LedgerEntryType` | 沿用充值、冲正、提现冻结 / 退回 / 出账；新增 `BET_LOCK`（可用 −、下注锁定 +）、`BET_SETTLE`（下注锁定 −）、`BET_LOST`（下注锁定 −）、`PAYOUT`（可用 +）、`FEE`（可用 −）、`REFUND`（下注锁定 −、可用 +）、`COMPENSATION`（可用 +），平台侧 `FEE_INCOME`、`SETTLE_DUST`（平台收入 +）、`COMPENSATION_EXPENSE`（补偿支出 −）。每种类型带"账户种类 + 每一项的方向"，`allows()` 检查 |
| `api/LedgerApi` | 新增 `applyAll`：一组变动同一个事务全部记或全部不记，涉及多个客户时先按用户 id 升序锁账户（架构方案第 4.2 节的锁顺序）。`apply` 增加三道检查：类型规则、金额不能为 0 / 不超过 8 位小数、**同一个幂等键换了账户或金额抛 `IllegalStateException`**（以前直接当成重复返回） |
| `api/PlatformLedgerApi`（新） | 平台收入、补偿支出的记账和余额查询；锁平台账户行（放在客户账户之后锁） |
| `api/LedgerQueryApi` | 新增 `mismatches()`（全库每个账户每一项：账本合计 ≠ 账户金额的列出来；账本里有不认识的项也列出来）、`marketTotals(marketId)`（按 `ref_market_id` 按类型和项合计，给 S5 彩池对账和结算收尾复核用） |
| `api/AccountSnapshot`、`LedgerCommand` | 快照有三项和 `balance()`（= 可用 + 下注锁定）；记账命令加可选的 `refMarketId`（保留原来 7 个参数的构造方法，钱包代码不用改） |
| `api/FundsApi` | 可提金额 = 可用余额（下注锁定、提现冻结的钱不能提） |
| `service/LedgerService` | 实现以上接口；改金额只有 `post()` 一处，和写账本在同一个事务 |
| `service/LedgerController` | `GET /api/ledger/account` 返回 `balance`（可用 + 下注中）、`available`、`betLocked`、`withdrawFrozen`；资金流水只看可用余额，下注等类型暂不列给客户端（客户端还没有对应的显示，S4、S5 加） |
| `LedgerMapper.xml` | 三项列名、平台账户（按生成列 `platform_key` 找）、`ref_market_id`、核对和按市场合计的 SQL；后台客户列表的余额 = 可用 + 下注锁定 |

| 改动 | 理由 |
|---|---|
| 每种流水类型写死"账户种类、项、方向"，记账前检查（`LedgerEntryType.allows`） | 下注、结算、退款、补偿在 S4～S7 由不同的人写，用错类型或方向（例如把派彩记到下注锁定）会悄悄破坏守恒；在账本层直接拒绝最便宜 |
| 同一个幂等键换了账户或金额时抛错（以前直接当成重复） | 这种情况只可能是程序错误（单号拼错、金额算错），当成重复会让错误的金额悄悄消失 |
| `applyAll`（一组变动同一事务、按用户 id 升序加锁） | 下注、结算都是"两项同时变"，放在一个调用里不会漏掉一半；锁顺序和架构方案第 4.2 节一致 |
| `LedgerQueryApi.mismatches()`、`marketTotals()` | 把"账本合计 = 余额"从测试里的 SQL 变成可以调用的核对，S5 的每日对账直接用；按市场合计是架构方案第 4.4 节要的 |
| 改手续费时也检查"小于最小提现金额" | 需求只写了"保存最小金额时校验"；只查一边的话，把手续费调高就能绕过 |
| 后台客户详情显示"下注中"，后台流水类型加名字 | 任务只要求客户端；后台已经返回这个字段，显示出来财务才看得到客户的钱在哪 |
| 账本 Mapper 只增不改的测试 | 架构方案第 3.1 节写了"测试扫描 Mapper XML"，S1 没有做 |
| 端到端主流程检查"下注中" | 保证接口字段和资产页在真实部署形态下也连上 |

## 1. 结论
- **裁决台**（resolve 模块 `resolve/platform/ResolveDesk`）：列表按分组（待提议、待确认、自动裁决失败、等待中、超时、公示中、争议中），超时的在前并带标红字段；**提议**（结果或作废 + 依据链接 1～5 个 + 存档截图 0～5 张 + 理由 ≤ 1,000 字，带结算预览）→ 有 `resolve:confirm` 的人**确认**（结果 → 公示中、争议窗口开始、通知 #10；作废 → 已作废、全额退款）或**退回**；也可以不等提议**直接确认**（同样高危）。同一时间只有一条待确认的提议。
- **E6 / E7**：裁决台标记"等待"（E6 等到原定开赛后 48 小时、E7 等到标记后 48 小时），等待期间不能提议；解除后重新计提议时限；到时间没解除系统作废（退款原因 `POSTPONED_48H` / `ABANDONED_48H`）。S8 体育自动化时由数据源触发同一个入口。
- **公示期满结算**（`PublicityService`，任务每 15 秒、租约 `resolve.publicity`）：公示中、争议截止时间已到、没有争议 → `ResultHandler.settle(…, PUBLICIZING)`。结算只在市场"正好在公示中"时开始，提交争议要求"结算还没开始"，两者在市场行锁上排队，**只会有一个生效**（并发测试实测两种结果都出现过，见第 4.2 节）。
- **争议**：只有在这个市场有有效持仓的客户、公示期内（收到时间 < 截止时间）、每人每市场一次（唯一键兜底）、理由必填 ≤ 1,000 字、可带一个链接；第一个争议让市场进入争议中（第 13 条边），之后到期也不会自动结算。有 `dispute:handle` 的人处理（高危）：**维持 / 改判后直接结算**（不再公示），**无法判定作废**；全部待处理的争议一起给结论（#15），改判给所有下注人发 #16。结论公开（不显示争议人）。
- **补偿**（E13，settle 模块 `settle/comp/CompensationService`）：只对已结算的市场；按"正确结果"重算每个客户应得，和实际拿到的比，**只补不扣**；客户流水 `COMPENSATION`、平台补偿支出账户（可以为负）、通知 #17；每个市场一次（唯一键 + 结算锁）；高危、审计 `settle.compensate`；报表里补偿支出单列、不冲减平台收入。
- **超时提醒**（SQ-14）：待提议、待确认、争议处理超时各发一次员工邮件（`FC_RISK_ALERT_EMAILS`）；新提议、新争议也发。按角色发在 S9。
- **客户端详情**：平台裁决的市场在公示中、争议中、已结算、已作废时有 `resolution`：结果、依据链接、理由、裁决人编号、实际开赛时间、争议截止时间、争议数、争议结论、本人的争议和能不能提交。截图不公开（D-86）。
- **SQ-10**：删除了 S5 的临时入口 `POST /api/admin/markets/{publicNo}/settle`（现在 404 / 405，端到端里检查）；人工作废 `POST /api/admin/markets/{publicNo}/void` 保留，业务改走裁决台（写裁决记录、待处理的争议一起结束）。
- **端到端主线**改为正式流程：提议 → 确认 → 公示 → 窗口到期 → 自动结算；新增争议改判 + 补偿的用例。两种形态都跑（第 5 节）。
- 迁移：`V15__platform_resolve.sql`（5 张表、9 个参数、7 个通知模板）。V1～V14 没有改。
- 本地实际执行：后端全量空库 verify、状态机穷举、并发、端到端两种形态、前端 lint / 单元测试 / 构建、索引检查、仓库品牌检查、gitleaks，结果见第 5 节。

## 12. 整合 2 补记（2026-10-25，`claude/integration-2`，PR #18）
- **发现并修复一个死锁**：PR #18 第一次 GitHub CI 的 `SettleConcurrencyTest`（下注、提现、结算、取消混合跑）报"InnoDB 死锁计数没有增加"，死锁在 `PlatformMapper.insertCaseIgnore`。根因：market 的状态跳转事务用默认隔离级别（可重复读），`ResolveMarketListener` 先 `CaseBook.sync`、再 `CaseBook.open`；sync 对还没有进度行的市场直接 `UPDATE resolve_case … WHERE market_id = ?`，可重复读下在主键末尾加了间隙锁，两个新市场同时进入待裁决时各自持有间隙锁、再各自插入，插入意向锁互相等待。本机用两个 mysql 会话按这个顺序手工复现了 `ERROR 1213`；新加的 `resolve/CaseBookGapLockTest`（两个线程都 sync 完再都 open）修复前稳定失败、修复后通过。

- 本机 S7 阶段两次全量都没有触发，是因为这个交错依赖两个事务的时间重叠，CI 机器上更容易出现。
